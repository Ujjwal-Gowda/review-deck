Part 1: The Numbers Every Engineer Must Memorize

Latency Hierarchy

  • L1 cache reference: 0.5 – 1 ns
  • RAM access: 100 ns
  • NVMe SSD random read: 100 µs (0.1 ms)
  • Same-datacenter network round-trip: 0.5 ms
  • Cross-region network round-trip (US to EU): 80 – 150 ms

Mental Math Shorthands

  • $1\text{ day} = 86,400\text{ seconds} \approx 10^5\text{ seconds}$
  • $1\text{ Million requests / day} \approx \mathbf{12\text{ RPS}}$
  • $100\text{ Million requests / day} \approx \mathbf{1,200\text{ RPS}}$
  • Peak Traffic Rule of Thumb: Multiply average RPS by $3\times$ to $5\times$.
  • $1\text{ KB} \times 1\text{M writes / day} \approx \mathbf{1\text{ GB / day}} \approx \mathbf{365\text{ GB / yr}}$.

Part 2: Full Walkthrough: Stadium Ticket Reservation Engine

Let's design a high-throughput ticketing platform (e.g. reserving 50,000 stadium seats in 60 seconds with 500,000 concurrent users without overselling).

1. Requirements & Scope

  • Functional: Browse events, view interactive seat layout, hold a seat for 10 minutes during checkout, complete purchase, release seat if timer expires.
  • Non-Functional: Zero Double-Booking (Strict Consistency over Seat State), High Availability on seat browsing, P99 latency < 200ms.

2. Back-of-Envelope Sizing

  • Peak Traffic: 500,000 active users searching seats = 25,000 Read RPS.
  • Write Traffic: 50,000 reservation attempts in first 10 seconds = 5,000 Write RPS.

4. The Deep Dive: The 10-Minute Seat Reservation Problem

Holding database row locks (SELECT FOR UPDATE) across a 10-minute human credit card checkout will exhaust all database connections and crash the database. Instead, use an Atomic Redis Lua Script with an automatic Time-To-Live (TTL):

-- atomic_seat_hold.lua
-- KEYS[1]: seat key (e.g. "event:42:seat:B12")
-- ARGV[1]: user_id
-- ARGV[2]: hold_duration_seconds (e.g. 600)

if redis.call("EXISTS", KEYS[1]) == 1 then
    return 0 -- Seat already held or sold!
else
    -- Atomically claim seat with 10-minute expiry
    redis.call("SET", KEYS[1], ARGV[1], "EX", ARGV[2])
    return 1 -- Hold acquired successfully!
end

If the user completes payment within 10 minutes, the backend records the confirmed sale in PostgreSQL. If the user closes their browser, Redis automatically expires the key after 600 seconds, releasing the seat instantly back to other fans without running background cleanup cron jobs.

Drill: How to handle Live Delivery Driver Geolocation tracking at 1M RPS? (Click to expand)

Question: 1,000,000 delivery drivers send GPS coordinates $(lat, lng)$ every 3 seconds. How do you store and query "find the 5 nearest drivers within 2km"?

Answer: Redis Geospatial Indices (Geohash / Sorted Sets)!

  • Never write 300,000 GPS updates per second to relational disk (PostGIS)! The write IOPS will destroy the database.
  • Store driver coordinates in Redis in-memory using GEOADD drivers:active <lng> <lat> <driver_id>.
  • Query nearby drivers using GEOSEARCH drivers:active FROMLONLAT <lng> <lat> BYRADIUS 2 km COUNT 5 ASC. Redis executes this spatial B-tree search in sub-millisecond memory!
