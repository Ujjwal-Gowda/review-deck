Every design decision trades something away. Practise making those trades explicitly.

AxisTension
Consistency ↔ availability / latencysynchronous replication and locks vs fast, stale-tolerant reads
Simplicity ↔ scalabilitya monolith with one database vs services, queues and shards
Cost ↔ performance / reliabilitymore replicas, regions and headroom cost money
Build ↔ buycontrol vs time-to-market (auth, search, payments)
Normalised ↔ denormalisedclean writes vs fast reads
Push ↔ pullreal-time fan-out vs on-demand computation

Practice problems (45 minutes each, using the method from this part)

  • URL shortener: ID generation (base62 of a counter vs random + collision check), a read-heavy cache, analytics written asynchronously.
  • Rate limiter: token bucket vs sliding window; per-user keys in Redis; atomicity with Lua; what happens when Redis is down (fail open or closed?).
  • Chat: WebSocket gateways, pub/sub between gateways, message storage by conversation, delivery and read receipts, offline push.
  • News feed: fan-out on write (precomputed timelines) vs fan-out on read; the celebrity problem forces a hybrid.
  • Food/grocery delivery (FreshOn): orders, stock reservation, rider assignment, live tracking, surge handling.

For each one: state the requirements and numbers, draw the diagram, walk the flows, list the failure modes, and name the trade-offs you chose and what would make you choose differently. That last step is what interviewers and real design reviews are looking for.
