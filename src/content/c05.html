The single most important abstraction: named, reusable, testable units of logic.

Why functions

A function packages logic behind a name and an interface (inputs → output). It lets you name an idea (is_valid_email says more than 12 lines of checks), reuse it, test it in isolation, and reason locally: to use sorted() you need its contract, not its internals.

def area(width: float, height: float) -> float:   # parameters (with type hints)
    """Return the area of a rectangle."""          # docstring: the contract
    return width * height

a = area(3, 4)          # arguments 3 and 4 are bound to the parameters
  • Parameters are the names in the definition; arguments are the values passed in a call.
  • A function without return returns None in Python (undefined in JS; void in C).
  • Default, keyword, and variadic arguments:
def greet(name, greeting="Hello", *extra, loud=False, **options):
    msg = f"{greeting}, {name}"
    return msg.upper() if loud else msg

greet("Asha")                          # 'Hello, Asha'
greet("Asha", "Hi", loud=True)         # 'HI, ASHA'
Python's most famous trap: mutable default arguments 
def add_item(item, bucket=[]):     # the [] is created ONCE, when def runs
    bucket.append(item)
    return bucket
add_item(1)   # [1]
add_item(2)   # [1, 2]   the same list is reused across calls!

def add_item(item, bucket=None):   # correct idiom
    if bucket is None:
        bucket = []
    bucket.append(item)
    return bucket

Scope: where a name is visible

Names defined inside a function are local: they exist only while that call runs, and don't clash with names elsewhere. Python looks names up with the LEGB rule: Local, then Enclosing function, then Global (module), then Built-in.

count = 0
def bump():
    count += 1     # UnboundLocalError! Assigning makes 'count' local to bump,
                   # and it's read before being assigned.
def bump_fixed():
    global count   # works, but global mutable state is a design smell:
    count += 1     # prefer passing values in and returning results out.

C, JS (let/const), Go, Rust and Java have block scope: a variable declared inside { } (an if or a loop) dies at the closing brace. Python has only function scope, so a variable assigned inside an if is still visible after it.

Pure functions and side effects

A pure function's output depends only on its inputs, and it changes nothing outside itself. area(3,4) is always 12. A side effect is anything else: printing, writing a file, mutating an argument, changing a global, reading the clock, making a network call.

Programs need side effects (that's the point), but push them to the edges. Keep the core logic pure (easy to test and reason about), and make a thin outer layer that does I/O. This is one of the most valuable design habits there is:

def summarize(orders: list[dict]) -> dict:          # pure: trivially testable
    total = sum(o["amount"] for o in orders)
    return {"count": len(orders), "total": total}

def main():                                           # impure shell: I/O only
    orders = load_orders_from_file("orders.json")
    print(summarize(orders))

The call stack

Each time a function is called, the runtime pushes a stack frame holding its parameters, local variables and the return address (where to continue afterwards). When the function returns, its frame is popped and its locals are gone.

def c(): return 1 Stack while c() runs (grows downward): def b(): return c() + 1 ┌──────────────┐ def a(): return b() + 1 │ main │ ← waiting for a() a() ├──────────────┤ │ a │ ← waiting for b() ├──────────────┤ │ b │ ← waiting for c() ├──────────────┤ │ c (running) │ └──────────────┘

This is exactly what a traceback shows you when there's an error: the stack at the moment of the crash, from outermost to innermost call. Read it bottom-up to find where it broke, and top-down to see how you got there.

Recursion

A function that calls itself. Each call gets its own frame and its own locals. Every recursive function needs:

  1. A base case that returns without recursing.
  2. A recursive case that moves toward the base case.
def factorial(n: int) -> int:
    if n <= 1:              # base case
        return 1
    return n * factorial(n - 1)     # smaller problem

def sum_nested(x) -> int:            # recursion shines on nested / tree-shaped data
    if isinstance(x, int):
        return x
    return sum(sum_nested(item) for item in x)

sum_nested([1, [2, [3, 4]], 5])      # 15

Trust the recursion: assume the smaller call works (the "recursive leap of faith"), and only check that (a) the base case is right and (b) you combine the result correctly. Deep recursion can overflow the stack (Python's default limit is about 1000 frames: RecursionError). Any recursion can be rewritten as a loop with an explicit stack; chapter 12 shows how.

def clamp(x, lo, hi):

def is_leap_year(y):

5.2 basic Recursive power(base, exp). Then make it O(log exp) using "square the half" (x^10 = (x^5)²).
def power(b, e):
    if e == 0: return 1
    half = power(b, e // 2)
    return half * half if e % 2 == 0 else half * half * b
5.3 think Towers of Hanoi: print the moves to move n discs from peg A to C. Don't look anything up. Use the recursive leap of faith.
def hanoi(n, src="A", dst="C", via="B"):
    if n == 0: return
    hanoi(n - 1, src, via, dst)      # move n-1 out of the way
    print(f"disc {n}: {src} -> {dst}")
    hanoi(n - 1, via, dst, src)      # put them back on top

2ⁿ − 1 moves. If this felt like magic, draw the call stack for n = 3.

5.4 think Draw the call stack for factorial(4) at its deepest point. How many frames? What does each hold?

Five frames: main, then factorial(4), (3), (2), (1). Each frame holds its own n and waits on the multiplication. factorial(1) returns 1, and each frame pops in turn: 2×1, 3×2, 4×6 = 24.
