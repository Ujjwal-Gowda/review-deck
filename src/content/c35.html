Understanding the JS runtime underneath, and a type system that exists only at compile time.

Mental model

  • TypeScript = JavaScript + static types. The compiler (tsc) checks types and then erases them: at runtime it's plain JS. That means no runtime checking, so validate external data (API responses, JSON) with a schema library such as zod.
  • The type system is structural: any value with the right shape fits.
  • The JS runtime: single-threaded event loop; objects and arrays are references; number is a 64-bit float (integers are exact only up to 2⁵³; use bigint beyond); prototypes underlie classes.
  • Where it runs: Browsers, Node.js, Deno, Bun, and serverless cloud edge environments.
// types: annotations, inference, unions, literal types
type Status = "placed" | "paid" | "shipped";
interface Item { sku: string; qty: number; pricePaise: number }
interface Order { id: number; items: Item[]; status: Status; note?: string }   // ? = optional

const total = (o: Order): number =>
  o.items.reduce((sum, i) => sum + i.qty * i.pricePaise, 0);

// discriminated union + exhaustive switch (the TS version of a Rust enum)
type Result<T> = { ok: true; value: T } | { ok: false; error: string };
function show(r: Result<number>): string {
  switch (r.ok) {
    case true:  return `value ${r.value}`;       // narrowed: r.value exists here
    case false: return `error ${r.error}`;
  }
}

// generics + utility types
function byId<T extends { id: number }>(xs: T[]): Map<number, T> {
  return new Map(xs.map(x => [x.id, x]));
}
type Draft = Partial<Order>;            // all fields optional
type Summary = Pick<Order, "id" | "status">;
type ReadonlyOrder = Readonly<Order>;

// async
async function load(id: number): Promise<Order> {
  const res = await fetch(`/api/orders/${id}`);
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return (await res.json()) as Order;   // 'as' is a PROMISE to the compiler, not a check. Validate!
}
const [a, b] = await Promise.all([load(1), load(2)]);   // run concurrently

Traps & Common Pitfalls

  • Compile-Time Traps (TypeScript-specific):
    • any switches off type checking completely and infects all downstream expressions. Always prefer unknown and narrow using type guards.
    • Forgetting to enable "strict": true in tsconfig.json, which turns off strict null checks and noImplicitAny.
    • Type assertion abuse: as TargetType is a blunt compiler override, not a runtime validation. Always validate external input with schema validators (Zod/Valibot).
  • Inherited Runtime Traps (JavaScript engine-level):
    • Unawaited promises: Forgetting await leaves you holding a pending Promise object instead of the resolved value.
    • Array.prototype.forEach is synchronous and ignores async callbacks; use for...of or Promise.all(xs.map(...)) instead.
    • Floating point precision: 0.1 + 0.2 !== 0.3 is an IEEE-754 runtime property, not a TypeScript bug.
    • Lexicographic sorting: [10, 5, 1].sort() sorts elements as strings (producing [1, 10, 5]); always pass an explicit comparator: (a, b) => a - b.

Clear-up path

  1. Understand the JS event loop, closures, this and promises first. That's where most TS confusion actually comes from.
  2. Read the official TypeScript Handbook end to end (narrowing, generics, and mapped/conditional types).
  3. Do the type-challenges repo (easy → medium) to master the type system.
  4. Build: a Node CLI with node --test; a small API with Hono or Express + zod; then read your own Remotion code again and explain every type.
