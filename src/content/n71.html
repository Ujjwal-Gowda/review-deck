The Real Mental Model of React

Most developers think of React as a template library that re-runs when variables change. In reality, React is a declarative state reconciler and runtime scheduler. You do not touch DOM nodes directly; you describe what the UI tree should look like for a given snapshot of state, and React determines the minimal set of physical DOM mutations required to bring the browser screen in sync.

Part 1: The Fiber Node & Double-Buffering Tree

In React 16+, every component instance is backed by a Fiber node—a JavaScript object representing a unit of work. Fibers form a singly linked list tree structure using three pointers:

  • child: Points to its first immediate child.
  • sibling: Points to its next sibling.
  • return: Points back to its parent (return destination after work finishes).
Why React Uses Double Buffering (Like Graphics Engines)

Video games never draw pixels directly to the active monitor buffer while computing physics, because users would see tearing and partial frames. They render the next frame onto an off-screen buffer, then swap pointers instantly.

React does the exact same thing: it keeps the Current Fiber Tree (reflecting what is currently visible on the screen) untouched while computing changes on a workInProgress Fiber Tree in memory. Only when all components finish rendering without errors does React swap the root pointer.

Part 2: How Hooks Actually Work (The Linked List)

Have you ever wondered why React forbids calling hooks inside if statements, loops, or nested functions? "React hooks must be called at the top level."

Because React does NOT store hook state in a hash map by name! Each Fiber node has a property fiber.memoizedState that points to the head of a singly linked list of Hook objects:

┌────────────────────────────────────────────────────────────────────────────────────────┐ │ Fiber Hook Linked List │ │ │ │ fiber.memoizedState │ │ │ │ │ ▼ │ │ ┌─────────────────┐ ┌─────────────────┐ ┌─────────────────┐ │ │ │ Hook 1: │ next │ Hook 2: │ next │ Hook 3: │ │ │ │ useState(count) │──────►│ useEffect(...) │──────►│ useRef(inputEl) │──► null │ │ │ memoized: 42 │ │ memoized: effect│ │ memoized: {cur} │ │ │ └─────────────────┘ └─────────────────┘ └─────────────────┘ │ └────────────────────────────────────────────────────────────────────────────────────────┘

When your component function executes on a re-render, React traverses this linked list one hook at a time using an internal pointer. If you place a hook inside an if statement and the condition evaluates to false on the second render, the hook order shifts! Hook 3 is read into Hook 2's slot, corrupting state across the entire component.

Part 3: The Hook Masterclass

import React, { useState, useEffect, useRef, useMemo, useCallback, useTransition } from "react";

interface Product {
  id: string;
  name: string;
  priceCents: number;
}

export function ProductCatalog({ categoryId }: { categoryId: string }) {
  // 1. Local State & Functional Updaters
  const [query, setQuery] = useState("");
  const [products, setProducts] = useState<Product[]>([]);
  
  // 2. Concurrent Transitions (React 18/19)
  // Keeps the input responsive while filtering 10,000 items in the background
  const [isPending, startTransition] = useTransition();

  // 3. Mutable Ref (Escape hatch that survives renders without re-rendering)
  const renderCountRef = useRef(0);
  renderCountRef.current++;

  // 4. Synchronization with External System (HTTP Network)
  useEffect(() => {
    let ignore = false; // Flag to prevent race conditions from out-of-order responses
    const controller = new AbortController();

    async function loadData() {
      try {
        const res = await fetch(`/api/products?cat=${categoryId}`, { signal: controller.signal });
        const data = await res.json();
        if (!ignore) {
          setProducts(data);
        }
      } catch (err: any) {
        if (err.name !== "AbortError") console.error("Fetch failed", err);
      }
    }

    loadData();

    // Cleanup function: runs before next effect execution and on component unmount
    return () => {
      ignore = true;
      controller.abort();
    };
  }, [categoryId]); // Only re-run when categoryId changes!

  // 5. Derived State (Compute during render! Do NOT put in useEffect!)
  const filteredProducts = useMemo(() => {
    return products.filter((p) => p.name.toLowerCase().includes(query.toLowerCase()));
  }, [products, query]);

  // 6. Non-urgent state update scheduled with useTransition
  const handleSearchChange = (e: React.ChangeEvent<HTMLInputElement>) => {
    const val = e.target.value;
    // Urgent update: update text field immediately
    setQuery(val);
    
    // Non-urgent update: low-priority render that can be interrupted by new keystrokes
    startTransition(() => {
      // background transition state if needed
    });
  };

  return (
    <div className="catalog">
      <input value={query} onChange={handleSearchChange} placeholder="Search products..." />
      {isPending && <span className="spinner">Updating results...</span>}
      <div className="grid">
        {filteredProducts.map((p) => (
          // Always use stable IDs as keys, NEVER array index!
          <div key={p.id} className="card">
            <h4>{p.name}</h4>
            <p>${(p.priceCents / 100).toFixed(2)}</p>
          </div>
        ))}
      </div>
    </div>
  );
}

Part 4: The 3 Deadliest React Anti-Patterns

1. Storing Derived State in `useEffect`

// ❌ CRITICAL ANTI-PATTERN: Wasted renders & state desync
const [items, setItems] = useState([]);
const [total, setTotal] = useState(0);

useEffect(() => {
  setTotal(items.reduce((s, i) => s + i.price, 0));
}, [items]); // Triggers a SECOND render cycle after every update!

// ✅ THE FIX: Derive during render!
const total = items.reduce((s, i) => s + i.price, 0);

{items.map((item, index) => (

// React assumes the FIRST element never moved,
// preserving internal input state and corrupting user form values!

// ✅ THE FIX:
{items.map((item) => (
  <TodoItem key={item.id} text={item.text} />

Drill: What is the Stale Closure Bug in React? (Click to expand) 
function Timer() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1); // Bug here!
    }, 1000);
    return () => clearInterval(id);
  }, []); // Empty dependency array!
  return <h1>{count}</h1>;
}

Question: Why does this timer get permanently stuck at 1 instead of counting up every second?

Answer: Stale Closure over the initial render scope!

Because the dependency array is [], the effect runs only once when Timer first mounts. The callback passed to setInterval captures the lexical variable count from the first render, where count === 0.

Every second, setInterval fires and evaluates setCount(0 + 1). It repeatedly sets the state to 1!

The Fix: Use the functional updater form: setCount(prev => prev + 1). The updater receives the current live value from React's internal fiber state, bypassing stale closures entirely!
