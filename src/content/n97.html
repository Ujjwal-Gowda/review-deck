Keeping data correct when several things happen at once.

BEGIN;
UPDATE stock  SET qty = qty - 2 WHERE sku = 'paneer' AND qty >= 2;   -- check rows affected = 1!
INSERT INTO order_items (order_id, sku, qty) VALUES (42, 'paneer', 2);
COMMIT;   -- both happen or neither does (on error: ROLLBACK)

Preventing lost updates

  1. Atomic updates: SET qty = qty - 1, not read-modify-write in application code.
  2. Conditional updates: … WHERE qty >= 2, then check the affected row count.
  3. Pessimistic locking: SELECT … FOR UPDATE locks the row until commit.
  4. Optimistic locking: a version column; UPDATE … SET version = version + 1 WHERE id = $1 AND version = $2, and retry if 0 rows changed.

Deadlocks: T1 locks A then wants B; T2 locks B then wants A. Postgres detects this and aborts one of them. Prevent it by locking in a consistent order (e.g. sort SKUs before updating stock). Keep transactions short: never wait for HTTP calls or user input while holding one.

Practice

97.1 basic In two psql sessions, reproduce a lost update with read-then-write, then fix it with an atomic UPDATE and with SELECT … FOR UPDATE.

Both sessions read qty=5 and both write 4, so one decrement is lost. UPDATE … SET qty = qty-1, or locking the row first, serialises them and gives 3.
