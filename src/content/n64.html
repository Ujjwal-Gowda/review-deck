How HTTPS gives you encryption, integrity and server identity, and what to do when certificates break.

What TLS provides

  • Confidentiality: nobody on the path can read the traffic (coffee-shop Wi-Fi, your ISP).
  • Integrity: nobody can modify it without detection.
  • Authentication: you're really talking to api.freshon.in, not an impostor.

The TLS 1.3 handshake (simplified)

client ── ClientHello (supported ciphers, key share, SNI: "api.freshon.in") ──► ◄── ServerHello (key share) + certificate chain + signature + Finished ── server both sides derive the same symmetric session keys (ECDHE key exchange: never sent over the wire) client checks: chain → a trusted root CA? name matches? not expired? signature valid? ── Finished ──► then application data, encrypted with AES-GCM or ChaCha20 (1 round trip total)

Asymmetric crypto (the certificate's key pair) proves identity and agrees on keys. Fast symmetric crypto then encrypts the data. Forward secrecy: ephemeral keys mean a server key stolen later can't decrypt recorded past traffic.

Certificates

A certificate binds a public key to domain names, and is signed by a Certificate Authority. Your OS and browser ship with about 150 trusted root CAs. Chain: leaf certificate (freshon.in) ← intermediate CA ← root CA. Let's Encrypt issues free 90-day certificates via the ACME protocol, which Caddy, Netlify and certbot automate.

openssl s_client -connect api.freshon.in:443 -servername api.freshon.in </dev/null | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
curl -vI https://site 2>&1 | grep -E 'expire|subject|issuer|SSL'

HSTS (Strict-Transport-Security) tells browsers to always use HTTPS for your site. mTLS means the client presents a certificate too; it's used between services.

Never

Never ship verify=False, rejectUnauthorized: false or InsecureSkipVerify: true. It silently removes the "authentication" guarantee, so any attacker in the middle can impersonate the server.
