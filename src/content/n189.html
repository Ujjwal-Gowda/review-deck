Most backend slowness is database slowness. A checklist to fix it.

  1. Find the expensive queries: pg_stat_statements sorted by total_exec_time (frequency × duration matters more than the single slowest query); slow-query logs (log_min_duration_statement = 200ms).
  2. Explain them (chapter 96): look for sequential scans on big tables, bad row estimates, sorts spilling to disk.
  3. Index for the real WHERE and ORDER BY patterns (chapter 95).
  4. Fix access patterns: N+1 queries become joins or batches; SELECT * becomes the needed columns; deep OFFSET pagination becomes cursors; many round trips become one query or a CTE.
  5. Connection pooling: a right-sized pool (roughly cores × 2–4 per database, not 500), plus PgBouncer for many clients.
  6. Cache hot, rarely changing reads (the catalogue, settings).
  7. Reduce write amplification: batch inserts (COPY, multi-row INSERT), drop unused indexes, avoid updating unchanged rows.
  8. Data lifecycle: archive or partition old data (partition by month, drop old partitions instead of DELETE).
  9. Hardware and config last: enough RAM for the working set, shared_buffers, fast disks.

Practice

189.1 basic Enable pg_stat_statements, run your app's test suite, and list the top 5 queries by total time.

SELECT query, calls, total_exec_time FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 5; Usually one or two queries dominate, so optimise those first.
