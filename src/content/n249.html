Writing technical documents that people actually read and use. Document types are covered in chapter 41.

  • Start with the reader and their task: "a new developer wants to run the app" or "on-call at 3 a.m. needs to restore the database". Write for that task only.
  • Bottom line up front: the answer or decision first, the details after.
  • Structure for scanning: headings that say something, short paragraphs, numbered steps for procedures, tables for comparisons, copy-pasteable commands.
  • Concrete over abstract: an example request and response beats a paragraph describing it.
  • Test your docs: follow your own README on a fresh machine or container. Every step that fails is a bug.
  • Keep docs close to the code (in the repo, updated in the same PR), and date or version them.
  • Edit ruthlessly: cut filler; one idea per sentence; active voice.
  • Diagrams for structure and flow (Mermaid in Markdown renders on GitHub).

A useful model is Diátaxis: tutorials (learning), how-to guides (tasks), reference (facts), and explanation (understanding). Keep them separate, since mixing them serves no reader well.
