Bundling data with behaviour, and when that helps versus hurts.

Core terms

TermMeaning
ClassA blueprint: defines the fields (data) and methods (behaviour) of a kind of object.
Object / instanceOne concrete thing made from a class, with its own field values.
MethodA function attached to a class; it receives the object (self / this).
ConstructorSets up a new object (__init__, constructor, new).
EncapsulationHiding internal state behind methods, so the object protects its own invariants.

A class that protects its invariants

class InsufficientStock(Exception): pass

class StockItem:
    def __init__(self, sku: str, qty: int = 0):
        if qty < 0:
            raise ValueError("qty must be >= 0")
        self.sku = sku
        self._qty = qty              # leading underscore: "internal, don't touch"

    @property
    def qty(self) -> int:            # read-only from outside
        return self._qty

    def remove(self, n: int) -> None:
        if n > self._qty:
            raise InsufficientStock(f"{self.sku}: have {self._qty}, need {n}")
        self._qty -= n               # the ONLY way qty goes down, so it can never go negative

    def __repr__(self):              # "dunder" methods hook into language features
        return f"StockItem({self.sku!r}, qty={self._qty})"

The invariant "qty is never negative" is guaranteed because the only way to change qty is through methods that check it. That's the real point of encapsulation: not secrecy, but making invalid states impossible. Access control varies by language: Java, C# and C++ have private/protected/public; Go uses capitalisation (Name is exported, name isn't); Rust has pub; Python relies on the underscore convention; JS has #private fields.

Inheritance and polymorphism

from abc import ABC, abstractmethod

class Payment(ABC):
    @abstractmethod
    def charge(self, amount: int) -> str: ...

class UPI(Payment):
    def __init__(self, vpa): self.vpa = vpa
    def charge(self, amount): return f"UPI collect ₹{amount/100:.2f} from {self.vpa}"

class Card(Payment):
    def __init__(self, last4): self.last4 = last4
    def charge(self, amount): return f"Card ****{self.last4} charged ₹{amount/100:.2f}"

def checkout(p: Payment, amount: int):
    print(p.charge(amount))          # POLYMORPHISM: works for any Payment, including future ones

for p in [UPI("asha@okbank"), Card("4242")]:
    checkout(p, 35200)

checkout never changes when you add Wallet or Cash. That is the core payoff of polymorphism: code that's open for extension but closed for modification.

Duck typing (Python, JS): "if it walks like a duck…". Any object with a charge method works; no base class required. Go formalises this with structural interfaces: a type satisfies an interface just by having the methods, with no implements keyword. Java and C# use nominal interfaces: you must declare implements Payment. Rust uses traits, implemented explicitly.

type Payment interface { Charge(amount int) string }
type UPI struct{ VPA string }
func (u UPI) Charge(amount int) string { return "UPI " + u.VPA }
// UPI satisfies Payment automatically. There's no class and no inheritance in Go at all.

Composition over inheritance

Inheritance couples a child tightly to its parent's internals. Change the parent and children break (the "fragile base class" problem). Deep hierarchies (Animal → Mammal → Dog → ServiceDog → …) become rigid. The widely accepted guideline is to prefer composition: give an object the parts it needs.

# inheritance: OrderService IS-A Logger? Nonsense.
class OrderService(Logger): ...

# composition: OrderService HAS-A logger and a payment method, both swappable
class OrderService:
    def __init__(self, payment: Payment, logger):
        self.payment, self.logger = payment, logger
    def place(self, amount):
        self.logger.info("placing order")
        return self.payment.charge(amount)

Use inheritance when there is a genuine "is-a" relationship, the hierarchy is shallow (1–2 levels), and subclasses are truly substitutable for the parent (the Liskov substitution principle: anywhere a Payment works, every subclass must work too).

Special (dunder) methods

from dataclasses import dataclass
@dataclass(order=True, frozen=True)     # generates __init__, __repr__, __eq__, __lt__, __hash__
class Money:
    paise: int
    def __add__(self, other): return Money(self.paise + other.paise)   # operator overloading
    def __str__(self): return f"₹{self.paise / 100:,.2f}"
print(Money(1050) + Money(250))          # ₹13.00
Trade-offs: OOP

Pros: models real-world entities naturally; encapsulation protects invariants; polymorphism makes code extensible; IDEs navigate it well; it's the dominant style in Java, C#, Python, Swift and Kotlin codebases.

Cons: tempts over-engineering (AbstractFactoryManagerImpl); deep inheritance is brittle; hidden mutable state inside objects makes concurrency and testing harder; not every problem is a "thing with behaviour". Many are data transformations, which suit a functional style better.

Rule of thumb: use classes for things with identity and invariants (an account, a connection, a cart). Use plain functions and data for transformations. Don't create a class that has one method and no state: that's just a function.

Exercises

13.1 basic Write a BankAccount with deposit, withdraw (no overdraft) and a transaction history. Balance must be read-only from outside.

Store self._balance and self._history = []; methods validate the amount > 0; withdraw raises if the amount is more than the balance; expose balance as a @property; append (kind, amount) to the history on each change.

13.2 basic Shapes: Circle, Rect and Triangle, each with area(). Compute the total area of a mixed list without any isinstance checks.

sum(s.area() for s in shapes). If you ever write if isinstance(s, Circle): … elif isinstance(s, Rect): …, that's the sign a polymorphic method is missing.

13.3 think The classic Square/Rectangle problem: is a Square a Rectangle? If Rectangle has set_width, what goes wrong when Square inherits from it?

Code that does r.set_width(5); r.set_height(4); assert r.area() == 20 breaks for a Square, because setting one side changes both. So Square isn't substitutable for a mutable Rectangle, which violates Liskov. Fixes: make shapes immutable, or don't use inheritance here. Mathematical "is-a" doesn't guarantee a behavioural "is-a".
