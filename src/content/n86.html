Access + refresh tokens

A short-lived access token (5–15 min) is sent on every API call. A long-lived refresh token (days) is stored securely (an HttpOnly cookie, or mobile secure storage) and used only to get new access tokens. Rotate the refresh token on every use and detect reuse (a reused old token means theft: revoke the whole family).

JWT pitfalls

  • JWTs are signed, not encrypted. Anyone can base64-decode the payload, so put no secrets in it.
  • Pin the algorithm on verify (reject alg: none and HS/RS confusion); check exp, iss and aud.
  • Don't keep them in localStorage (XSS can read it); use HttpOnly cookies for browsers.

OAuth 2.0 and OpenID Connect ("Log in with Google")

1. your app → redirect the browser to Google /authorize?client_id&redirect_uri&scope=openid email&state&code_challenge (PKCE) 2. the user logs in at GOOGLE (your app never sees the password) and consents 3. Google → redirect back to redirect_uri?code=…&state=… (check that state matches: CSRF protection) 4. your SERVER exchanges code + code_verifier (+ client secret) → access_token + id_token (a JWT: who the user is) 5. verify the id_token → find or create the local user → create YOUR session as usual

OAuth is for authorisation (the app may access the user's Google Drive). OIDC adds authentication (the id_token says who they are). PKCE protects the code exchange, and is required for mobile and SPAs.

Practice

86.1 basic Decode a JWT from any site you use (DevTools → Application → storage) at jwt.io. What's in the payload, and why isn't it secret?

You'll see sub, exp, iat, roles and so on. It's only base64url-encoded; the signature prevents tampering, not reading. Never put secrets in it.
