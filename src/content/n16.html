Debugging as a repeatable method, plus the debuggers for all five of your languages.

Chapter 15 covers reading tracebacks and the scientific method. This chapter is the toolkit and the harder cases.

The method, in one loop

reproduce → minimise → observe (expected vs actual) → hypothesise → test the hypothesis → fix the cause → add a regression test ▲ │ └──────────────────────── hypothesis wrong ─────────────────────────────┘
  • Minimise: shrink the failing input and delete unrelated code until the bug is small enough to see. Half of all bugs get solved at this step.
  • Bisect everything: the data (which record breaks it?), the code (comment out halves), time (git bisect), and config (which env var?).
  • Question your assumptions: "it can't be X" is where the bug usually is. Print the thing you're sure about.
  • Check what changed: git diff, git log -p, dependency upgrades, config, data, the environment.

Logging that helps you debug

import logging
log = logging.getLogger(__name__)
log.info("order placed", extra={"order_id": o.id, "total": o.total})   # structured: searchable by field
log.exception("payment failed")    # inside except: logs the full traceback

Log at the boundaries (inputs, outputs, decisions, errors) and include identifiers (request ID, order ID). Never log secrets or passwords.

Exercises

16.1 basic Put a conditional breakpoint in a loop over 1,000 items so it stops only at item 737. Do it in pdb and in Delve.

pdb: b file.py:12, i == 737. Delve: break file.go:12 then condition 1 i == 737.

16.2 think Create a tiny git repo with 20 commits where one introduces a bug that a test detects. Find it with git bisect run.

git bisect start HEAD HEAD~20 && git bisect run python3 -m pytest -q. Git binary-searches: about 5 test runs instead of 20.
