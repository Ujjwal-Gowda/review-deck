Defining the entities and the interfaces between components before choosing technology.

  1. Entities and relationships: Store, Product, Order, OrderItem, Rider, Delivery. Which ones are hot? Which are large?
  2. Core APIs for the key use cases, as signatures:
POST /orders            {store_id, items[], address_id, idempotency_key}  → 201 {order_id, eta}
GET  /orders/{id}                                                          → {status, items, rider?}
GET  /stores/{id}/orders?status=pending&cursor=…                          → paginated list
POST /deliveries/{id}/location  {lat, lng, ts}   (rider app, every 5 s)    → 204
WS   /orders/{id}/live                                                     → status + location events
  • Note which calls are synchronous, and which work happens asynchronously (events: OrderPlaced → reserve stock, notify store, assign rider).
  • Mark idempotency, pagination, authentication and rate limits on each API.
  • High-frequency writes (rider locations) often deserve a different path from core transactions (orders): a separate store, batching, or approximate data.
