Running work outside the request: retries, scheduling, and not doing anything twice.

import { Queue, Worker } from "bullmq";                        // Redis-backed jobs for Node
const invoices = new Queue("invoices", { connection });
await invoices.add("render", { orderId: 42 }, {
  jobId: "invoice-42",                          // dedupe: adding the same jobId again is a no-op
  attempts: 5, backoff: { type: "exponential", delay: 2000 },
  removeOnComplete: 1000,
});
new Worker("invoices", async job => {
  const pdf = await renderInvoice(job.data.orderId);
  await storage.put(`invoices/${job.data.orderId}.pdf`, pdf);   // idempotent: re-running overwrites the same key
}, { connection, concurrency: 4 });
await invoices.upsertJobScheduler("daily-report", { pattern: "0 23 * * *" }, { name: "report" });   // cron
-- the same idea with Postgres only: many workers, no double-processing
UPDATE jobs SET status = 'running', started_at = now()
WHERE id = (SELECT id FROM jobs WHERE status = 'queued' ORDER BY id
            FOR UPDATE SKIP LOCKED LIMIT 1)
RETURNING *;

Design rules

  • Idempotent jobs: safe to run twice (upserts, deterministic keys, "already done?" checks).
  • Small payloads: pass IDs, not whole objects; load fresh data inside the job.
  • Transactional outbox: to enqueue reliably with a DB write, insert the job row in the same transaction, and have a relay publish it. Otherwise a crash between "commit" and "enqueue" loses the job.
  • Set timeouts, cap retries, send failures to a dead-letter queue, and alert on it. Monitor queue depth and job age.
  • Graceful worker shutdown: finish the current job on SIGTERM.

Practice

91.1 basic Implement a Postgres-backed job queue with FOR UPDATE SKIP LOCKED, and run 3 workers to show each job runs exactly once.

Use a jobs(id, status, payload, attempts) table. Each worker loops: claim one job in a transaction with SKIP LOCKED, process it, mark it done, commit. Count the executions per job to verify.
