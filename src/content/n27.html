Using every core. When parallelism pays off, when it can't, and how each language does it.

Chapter 26 covers concurrency, correctness and races. This chapter is about speed.

Amdahl's law: the ceiling

If a fraction p of the work can run in parallel on N cores: speedup = 1 / ((1 − p) + p/N). With p = 0.9, 12 cores (your Ryzen) give 1/(0.1 + 0.075) ≈ 5.7×, and infinite cores cap at 10×. The serial part dominates quickly, so first shrink the serial part (I/O, locking, merging results).

Why parallel code is often slower than you expect

  • Overhead: starting processes, and pickling/copying data between them. Tiny tasks cost more to ship than to compute, so batch them.
  • Memory bandwidth: cores share RAM bandwidth. Memory-bound loops stop scaling after a few cores.
  • False sharing: two cores writing different variables that sit on the same 64-byte cache line ping-pong that line between them. Pad or separate per-thread data.
  • Contention: one shared lock or counter serialises everything. Use per-worker accumulators and merge at the end (map-reduce).
  • Oversubscription: more CPU-bound threads than cores just adds context switching. Size pools to the core count for CPU work; use larger pools for I/O.
  • RAM limits: 12 workers each loading a big file can exhaust your 7 GB and push the machine into swap.
Checklist

Profile first → make sure the work really is CPU-bound → parallelise the outermost independent loop → use a pool sized to the cores → give each worker coarse chunks → merge results at the end, not under a lock → measure the actual speedup against Amdahl's prediction.

27.1 think Hash every file in a directory tree (SHA-256) in Go with a worker pool, and compare 1, 2, 4, 8 and 12 workers. Where does it stop scaling, and why?

On an NVMe drive with small files it usually scales to around the core count (CPU-bound hashing). With big files, disk bandwidth caps it early. On your failing HDD, it would be seek-bound from about 2 workers onward. Measuring tells you which resource is the bottleneck.
