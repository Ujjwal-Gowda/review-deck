Storing and searching embeddings: the retrieval half of RAG and semantic search. The AI side is covered in the RAG part.

CREATE EXTENSION vector;                                    -- pgvector
CREATE TABLE docs (id bigserial PRIMARY KEY, store_id int, body text, embedding vector(1024));
CREATE INDEX ON docs USING hnsw (embedding vector_cosine_ops);   -- approximate nearest-neighbour index
SELECT id, body, 1 - (embedding <=> $1) AS similarity          -- <=> cosine distance, <-> L2, <#> inner product
FROM docs WHERE store_id = 7                                 -- metadata filter alongside the vector search
ORDER BY embedding <=> $1 LIMIT 5;

How ANN indexes work

  • Exact nearest neighbours means comparing against every vector: O(n × dimensions). That's too slow beyond ~100K vectors.
  • HNSW builds a multi-layer "small-world" graph and greedily walks toward the query. Fast and high-recall, but memory-hungry. Tunables: m, ef_construction, and hnsw.ef_search (higher means better recall, slower).
  • IVF clusters the vectors and searches only the nearest clusters. Less memory, and needs training.
  • Quantisation (int8, binary, product quantisation) shrinks vectors 4–32×, with some recall loss.

Sizing

1M vectors × 1024 dims × 4 bytes ≈ 4 GB of raw floats, plus the HNSW graph overhead. halfvec (float16) halves that.

Run exact search with the index disabled (SET enable_indexscan=off) as ground truth, then compare the top 10 overlap. Raising hnsw.ef_search should push recall close to 100%.
