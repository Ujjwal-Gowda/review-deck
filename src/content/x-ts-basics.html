Master TypeScript's static type system: understand erased types, structural typing, type inference, union and intersection types, the semantics of unknown/any/never, and control-flow type narrowing.

1. Learning Objectives

  • Type Erasure: Explain why TypeScript types disappear completely during compilation and why static types cannot validate incoming network or file data at runtime.
  • Structural Typing: Compare TypeScript's structural type system ("shape-based compatibility") with nominal type systems (Java, C#).
  • Type Inference & Annotations: Identify when to let the compiler infer types automatically and when explicit annotations prevent type widening or enforce public contracts.
  • Type Taxonomy: Contrast unknown, any, never, and void, and choose the correct top and bottom types for unvalidated inputs and unreachable branches.
  • Control Flow Analysis & Narrowing: Narrow union types using typeof, instanceof, in, equality guards, and custom type predicates.
  • Strict Nullability: Leverage strictNullChecks to eliminate "cannot read properties of undefined" runtime crashes.

2. Prerequisites & Mental Model

TypeScript is not a new programming language; it is a static type checker layered on top of JavaScript. Understanding the compile-time vs runtime boundary is the most important concept in TypeScript:

  • Compile Time (TypeScript): The TypeScript compiler (tsc) parses your code, checks types, verifies assignability, and generates diagnostic errors. Once type checking succeeds, all types, interfaces, type aliases, and generic parameters are completely erased!
  • Runtime (JavaScript Engine): The browser or Node.js executes pure, standard JavaScript. The JavaScript engine has zero awareness of your TypeScript types.
  • Consequence: TypeScript cannot protect you against malformed JSON from an API, corrupted database records, or invalid user inputs unless you implement explicit runtime boundary validation (e.g. with Zod or manual guard checks).
Mental Model: Think of TypeScript as an architectural blueprint inspector. The inspector verifies the blueprints before construction begins. But once the building is erected, the blueprints are filed away—the actual building stands or falls based on the physical materials (the JavaScript runtime).

3. Structural Typing: "Duck Typing" at Compile Time

Unlike nominal languages (like Java or C#) where two classes with identical fields are incompatible unless they share a named class or interface inheritance, TypeScript uses structural typing: two types are compatible if they share the same structure (properties and types).

interface Point2D {
  x: number;
  y: number;
}

interface Coordinate {
  x: number;
  y: number;
}

function renderPoint(p: Point2D) {
  console.log(`Point at (${p.x}, ${p.y})`);
}

const coord: Coordinate = { x: 10, y: 20 };
// Valid! Coordinate is structurally identical to Point2D:
renderPoint(coord);

// Excess Property Checking on Object Literals:
// Passing an inline literal with extra fields throws a compiler error:
// renderPoint({ x: 10, y: 20, z: 30 }); // Error: Object literal may only specify known properties!

// But passing an existing variable with extra fields is permitted (structural subtyping):
const point3D = { x: 10, y: 20, z: 30 };
renderPoint(point3D); // Valid! point3D has at least x and y.

4. Primitive Types, Arrays & Tuples

TypeScript mirrors JavaScript's primitive types and adds powerful collection types:

TypeScript Type Example Annotation Key Semantics
number let count: number = 42; All numbers (integers, floats, NaN, Infinity).
string let name: string = "Alice"; All string values.
boolean let isValid: boolean = true; true or false.
Array<T> / T[] let items: string[] = ["a", "b"]; Homogeneous list of elements.
Tuple [T, U] let pair: [string, number] = ["id", 1]; Fixed-length array where elements at specific indices have defined types.
Readonly Array let fixed: readonly number[] = [1, 2]; Array methods that mutate (push, pop, splice) are forbidden at compile time.

5. Union Types (|) & Intersection Types (&)

Union and intersection types allow precise modeling of flexible data:

  • Union Types (A | B): Represents a value that can be either type A OR type B. You can only safely access properties common to both types without prior narrowing.
  • Literal Types: Narrow primitives to exact allowed values (e.g. type HttpMethod = "GET" | "POST" | "PUT" | "DELETE").
  • Intersection Types (A & B): Combines all properties of both types together. Used for mixins and composite models.
type Status = "idle" | "loading" | "success" | "error";

interface Timestamps {
  createdAt: Date;
  updatedAt: Date;
}

interface UserProfile {
  id: string;
  name: string;
}

// Intersection: combines all properties
type PersistedUser = UserProfile & Timestamps;

const user: PersistedUser = {
  id: "u-101",
  name: "Sarah",
  createdAt: new Date(),
  updatedAt: new Date()
};

6. Type Hierarchy: unknown vs any vs never

Understanding TypeScript's top and bottom types is critical for type safety:

Type Position in Hierarchy Compiler Restrictions Correct Production Use Case
unknown Top Type (Safe) Can hold any value, but you cannot read properties, call it, or pass it to typed functions without explicit type narrowing. Always prefer for untrusted external data (parsed JSON, HTTP responses, user input).
any Escape Hatch (Unsafe) Disables the type checker completely. Any operation is permitted at compile time, deferring crashes to runtime! Avoid in production code. Only for temporary migrations or debugging.
never Bottom Type (Empty) Represents a state that can never occur. No value (other than never itself) is assignable to never. Exhaustive switch/match checking; functions that throw or never return.
void Unit Type Represents the return value of functions that do not return an explicit value. Function signatures that perform side effects without returning data. 
// [FAIL] Unsafe: using any
function processAny(payload: any) {
  payload.sendEmail(); // Compiles cleanly, but crashes at runtime if method doesn't exist!
}

// [OK] Safe: using unknown with narrowing
function processUnknown(payload: unknown) {
  // payload.sendEmail(); // Error: 'payload' is of type 'unknown'.
  if (typeof payload === "object" && payload !== null && "sendEmail" in payload) {
    // Narrowed safely!
    (payload as { sendEmail: () => void }).sendEmail();
  }
}

7. Control Flow Analysis & Type Narrowing

The TypeScript compiler tracks code branches and narrows broad union types into specific subtypes:

// 1. typeof narrowing (for primitives)
function formatInput(val: string | number) {
  if (typeof val === "number") {
    return val.toFixed(2); // Narrowed to number!
  }
  return val.trim(); // Narrowed to string!
}

// 2. instanceof narrowing (for classes and errors)
function handleAction(err: Error | string) {
  if (err instanceof Error) {
    console.error("Stack:", err.stack);
  } else {
    console.warn("Error message:", err);
  }
}

// 3. in operator narrowing (for object property presence)
interface Admin { role: "admin"; permissions: string[]; }
interface Member { role: "member"; teamId: string; }

function authorize(user: Admin | Member) {
  if ("permissions" in user) {
    console.log("Admin permissions:", user.permissions);
  } else {
    console.log("Member team:", user.teamId);
  }
}

8. Discriminated Unions & Exhaustive Checking

A discriminated union (or tagged union) pairs multiple object types sharing a common literal property (the "discriminant"). When combined with the never type, it guarantees exhaustive handling of all cases at compile time:

type NetworkState =
  | { state: "idle" }
  | { state: "loading" }
  | { state: "success"; data: string[] }
  | { state: "error"; error: Error };

function renderView(s: NetworkState): string {
  switch (s.state) {
    case "idle":
      return "Press Start to begin.";
    case "loading":
      return "Fetching data, please wait...";
    case "success":
      return `Loaded ${s.data.length} items.`;
    case "error":
      return `Failed: ${s.error.message}`;
    default: {
      // Exhaustive checking guard:
      // If a new variant (e.g. 'paused') is added to NetworkState,
      // the compiler throws a compile-time error here because s is NOT assignable to never!
      const _exhaustive: never = s;
      throw new Error(`Unhandled state: ${_exhaustive}`);
    }
  }
}

9. Custom Type Predicates: val is T

When type checking logic is complex, encapsulate the guard in a function returning a Type Predicate:

interface ApiResponse {
  status: "ok";
  payload: Record;
}

// User-defined type predicate:
function isApiResponse(data: unknown): data is ApiResponse {
  return (
    typeof data === "object" &&
    data !== null &&
    (data as Record).status === "ok" &&
    typeof (data as Record).payload === "object"
  );
}

// Usage in application code:
function parseServerMessage(raw: unknown) {
  if (isApiResponse(raw)) {
    // Compiler now knows raw is definitely an ApiResponse!
    console.log("Valid payload keys:", Object.keys(raw.payload));
  } else {
    console.error("Invalid server payload shape");
  }
}

10. Common Gotchas & Anti-Patterns

  • Unjustified Type Assertions (as Type): The as operator tells the compiler "trust me, I know better than you." If your assertion is wrong, TypeScript will not protect you from runtime crashes. Prefer narrowing or schema parsing over assertions.
  • Assuming Types Validate Runtime Input: Types like interface User only exist before compilation. An incoming HTTP request with missing fields will bypass TypeScript entirely unless parsed at runtime.
  • Overusing any: Using any creates infectious "holes" in your type safety, causing un-typed values to spread across your entire codebase. Use unknown instead.
  • Using Function or Object as Types: The global Function type accepts any function without type-checking arguments or return values. Use specific signatures: (...args: unknown[]) => void.

12. Practical Verification Drill

Build a safe, strictly typed JSON parser utility:

  • Signature: function safeJsonParse<T>(raw: string, validator: (val: unknown) => val is T): { ok: true; data: T } | { ok: false; error: Error }
  • Safely execute JSON.parse(raw) inside a try/catch.
  • Run the provided validator type predicate on the parsed output.
  • Return a discriminated union result so callers must check result.ok before accessing result.data.
  • Verify that malformed JSON strings and valid JSON strings with incorrect schema shapes are rejected cleanly with descriptive errors.
