Protecting services from overload, abuse and noisy neighbours, fairly.

Algorithms

AlgorithmHowBehaviour
Fixed windowcount per key per minutesimple; allows a double burst at window edges
Sliding window (log or counter)weight the previous window by how much of it overlapssmooth, and cheap in its counter form
Token buckettokens refill at rate r up to capacity b; each request spends oneallows bursts up to b while averaging r. The usual choice.
Leaky bucketa queue drained at a constant ratesmooths output traffic
Concurrency limitat most N requests in flightprotects expensive or slow endpoints; adapts to latency
class TokenBucket:                                   # in-process; use Redis + Lua for many instances
    def __init__(self, rate: float, capacity: int):
        self.rate, self.capacity, self.tokens, self.t = rate, capacity, capacity, time.monotonic()
    def allow(self) -> bool:
        now = time.monotonic()
        self.tokens = min(self.capacity, self.tokens + (now - self.t) * self.rate); self.t = now
        if self.tokens >= 1: self.tokens -= 1; return True
        return False

Where to enforce

  • Edge (CDN, WAF, reverse proxy): coarse per-IP limits against floods and scrapers.
  • API gateway or middleware: per API key, user or tenant; plan-based quotas.
  • In front of expensive things: login and OTP (anti-brute-force), SMS sending (cost), LLM calls (tokens), reports.
  • Outbound: respect third-party limits with a client-side limiter plus a queue.

Responses and fairness

Return 429 Too Many Requests with Retry-After and RateLimit-Limit/Remaining/Reset headers, so well-behaved clients back off. Limit per tenant so one busy store can't starve the others. Under real overload, shed load by priority: keep checkout, drop analytics (Resilience). Redis patterns are in Redis.

Practice

0.1 basic Implement a Redis token bucket as a Lua script, so it's atomic across many API instances, and test it with 3 instances hitting one key.

Store tokens and ts in a hash; the script computes the refill, decides, updates, and sets an expiry, all in one EVAL. With 3 instances firing, the total allowed per second stays at the rate: no races, because the Lua script runs atomically.
