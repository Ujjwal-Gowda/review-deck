A pull request is a proposal plus a conversation. Make yours easy to review and quick to merge.

The flow

branch → small commits → push → open PR (draft if early) → CI runs → review → address feedback → approve → merge → delete branch → deploy

What makes a PR easy to review

  • Small: under about 400 changed lines. Review quality collapses on large diffs. Split refactors from behaviour changes, and stack PRs if you need to.
  • One purpose: "Add zone-based delivery fees", not "fees + a renamed util + a dependency bump".
  • Self-reviewed first: read your own diff on GitHub before requesting review. You'll catch half the comments yourself.
  • Green CI before you ask for anyone's time.

A description template

## What
Zone-based delivery fees: free above ₹499 in central zones, ₹30 flat elsewhere.

## Why
Fixes #87. Flat fee was losing money on outskirt deliveries.

## How
- New FeeRule strategy per zone (orders/fees.ts)
- Zone added to Order; migration 0012 backfills "central"

## Testing
- Unit tests for each rule incl. the ₹499 boundary
- Manually placed orders in both zones on staging

## Risk / rollout
Behind FEATURE_ZONE_FEES flag; off by default.

Responding to review

Reply to every comment, whether with a fix or a reasoned disagreement. Push fixes as new commits during review (easier to re-review) and squash at merge. Don't take comments personally: the review is of the code, not of you.
