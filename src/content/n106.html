Testing your code together with the real things it talks to: databases, queues, HTTP.

Unit tests with fakes (chapter 105) can't catch wrong SQL, missing migrations, transaction bugs or serialisation mismatches. Integration tests run against real dependencies, usually in containers.

func TestOrderRepo(t *testing.T) {
    ctx := context.Background()
    pg, err := postgres.Run(ctx, "postgres:17", postgres.WithDatabase("test"),   // testcontainers-go
        postgres.BasicWaitStrategies())
    if err != nil { t.Fatal(err) }
    t.Cleanup(func() { pg.Terminate(ctx) })
    dsn, _ := pg.ConnectionString(ctx, "sslmode=disable")
    db := mustMigrate(t, dsn)                         // run the REAL migrations
    repo := NewRepo(db)
    id, err := repo.Create(ctx, Order{StoreID: 7, Items: []Item{{SKU: "milk", Qty: 2}}})
    require.NoError(t, err)
    got, _ := repo.Get(ctx, id)
    require.Equal(t, 2, got.Items[0].Qty)
}

Keeping them fast and isolated

  • Start the container once per test run (package or suite level), not per test.
  • Isolate each test: wrap it in a transaction that's rolled back, truncate tables, or use a fresh schema or database per test.
  • Fixtures / factories build valid test data in one line (makeOrder({status: "paid"})). Keep them minimal and explicit.
  • Test the HTTP layer with an in-process server (Go httptest, FastAPI TestClient, supertest) instead of a real port.
  • Stub only third-party services you don't control (payment gateway, SMS), using recorded responses or a local fake server (WireMock, MSW).

Contract tests (Pact) check that a client and a service agree on request and response shapes without running both together, which is useful between separately deployed services.
