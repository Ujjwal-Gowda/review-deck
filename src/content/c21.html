SOLID

  • Single responsibility: a module has one reason to change.
  • Open/closed: open for extension, closed for modification (via polymorphism, chapter 13).
  • Liskov substitution: subtypes must be usable anywhere their parent is.
  • Interface segregation: many small interfaces beat one fat one.
  • Dependency inversion: depend on abstractions, and pass dependencies in (dependency injection) rather than constructing them inside. This is what makes code testable.
class ReportService:                     # hard-wired: untestable without a real DB and email
    def run(self): db = PostgresDB(); ...; SmtpMailer().send(...)

class ReportService:                     # injected: tests pass fakes, production passes real ones
    def __init__(self, db, mailer): self.db, self.mailer = db, mailer

Architecture

  • Layered / hexagonal (ports and adapters) / clean architecture: the core domain logic has no dependencies on frameworks, databases or UI; adapters plug in at the edges.
  • Monolith vs microservices: a monolith is simple to build, deploy and debug, and is the right default. Microservices scale teams and components independently but add network failures, distributed data and ops cost. Split only when you have a real reason.
  • Code smells: long functions, long parameter lists, deep nesting, god classes, feature envy, primitive obsession, shotgun surgery (one change touches 12 files). The fix is refactoring: changing structure without changing behaviour, in small steps, with tests passing after each.

Naming and readability

Names should reveal intent (days_until_expiry, not d). Booleans read as questions (is_paid, has_stock). Functions are verbs (calculate_total). Name length should match scope size. Comments should explain why, never what. Keep functions small enough to see at once, and at one level of abstraction.

Practice

33.1 think Find the longest function in any project of yours and refactor it into smaller functions with intention-revealing names, keeping behaviour identical.

Extract steps into named functions, replace nesting with guard clauses, and pass data in and out rather than sharing state. Verify with tests (or add some first). Behaviour must not change: that's the definition of a refactor.
