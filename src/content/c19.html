Four philosophies of failure, and how to design for it.

f, err := os.Open("stock.csv")          // Go: errors are ordinary return values
if err != nil {
    return fmt.Errorf("loading stock: %w", err)   // wrap with context, pass it up
}
defer f.Close()
fn load(path: &str) -> Result<String, std::io::Error> {
    let text = std::fs::read_to_string(path)?;   // '?' = if Err, return it right away
    Ok(text.trim().to_string())
}
match load("stock.csv") {
    Ok(t) => println!("{t}"),
    Err(e) => eprintln!("failed: {e}"),
}
Trade-offs
StrategyProsCons
Exceptions (Python, Java, JS, C#)The happy path reads cleanly; errors propagate automaticallyInvisible control flow: any call might throw, and the signature doesn't say so; easy to forget to handle
Error values (Go)Explicit, visible, simpleVerbose (if err != nil everywhere); easy to ignore an error by accident
Result/Option types (Rust, Haskell, Swift)Explicit and enforced by the compiler; ? keeps it conciseType plumbing; a learning curve
Return codes + errno (C)Zero overheadTrivially ignored; no context

Design principles (in any language)

  • Recoverable vs unrecoverable. A missing file or bad user input is expected: handle it. A broken invariant is a bug: crash loudly (panic!, assert). Don't try to "recover" from bugs.
  • Fail fast: validate at the boundary (API input, config load) so bad data never gets deep inside.
  • Add context as errors propagate: "loading stock: open stock.csv: permission denied" beats "permission denied".
  • Handle an error once: either handle it or pass it up, not log-and-rethrow at every layer.
  • Clean up on every path: with, defer, finally, RAII/Drop.
  • In distributed systems: retries with exponential backoff + jitter, timeouts on every network call, idempotency (repeating a request is safe; vital for payments), and circuit breakers.
