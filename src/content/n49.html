Reviewing code well: what to look for, in what order, and how to say it.

Code review is also the most direct way to use the foundation you're rebuilding: every chapter so far is a lens for reading code. And reviewing AI-generated code is now a core daily skill.

Review in passes, from biggest to smallest

  1. Understanding: read the description. Is the problem real, and is this the right approach at all? (Catching a wrong design here saves the most time.)
  2. Correctness: edge cases (empty, zero, huge, unicode, concurrency), error paths, off-by-ones, null handling, race conditions, transactions around multi-step writes.
  3. Security: input validation, injection, authorisation checks, secrets, what gets logged (chapter 162).
  4. Tests: do they cover the change and its edge cases? Would they fail if the code were wrong?
  5. Design: boundaries, naming, duplication, complexity, fit with the existing architecture.
  6. Performance: queries in loops (N+1), unbounded memory, missing indexes, only where it matters.
  7. Style: leave it to formatters and linters. Humans shouldn't argue about commas.

Also praise good things specifically. Approve with minor comments when you trust the author to fix them.

A checklist to keep by your desk

□ I can explain what this change does and why, in one sentence
□ Empty / one / many / huge / invalid inputs are handled
□ Errors are handled once, with context; nothing silently swallowed
□ No secrets, no PII in logs; authz checked server-side
□ Resources closed (files, connections); timeouts on network calls
□ Concurrency: shared state protected; no await inside a lock
□ Tests would fail if the logic broke
□ Names reveal intent; no dead code or debug prints
□ Docs/config/migrations updated alongside the code

Reviewing AI-generated code

Apply the same checklist more strictly. AI code is fluent, so it looks right. Common failure modes: invented APIs or options, subtly wrong edge cases, swallowed errors, missing authorisation checks, over-engineering, and plausible but untested logic. Rule from chapter 0: never merge a line you couldn't have written and can't explain.

def get_user_orders(user_id):
    orders = db.execute(f"SELECT * FROM orders WHERE user_id = {user_id}")
    result = []
    for o in orders:
        o["items"] = db.execute(f"SELECT * FROM items WHERE order_id = {o['id']}")
        result.append(o)
    return result

blocking: SQL injection via f-strings. Use parameterised queries. blocking (perf): an N+1 query, one per order; use a JOIN or WHERE order_id = ANY(%s). question: is there an authorisation check that the caller may see this user's orders? Also a nit: SELECT * couples the code to the schema, so list the columns.
