Cloud identity and access: who (or what) can do which action on which resource.

ConceptMeaning
Principala user, a group, or a role (an identity that workloads and people assume temporarily)
Policya JSON document: Effect (Allow/Deny) + Action + Resource (+ Condition)
Evaluationdefault deny → an explicit Allow grants it → an explicit Deny always wins
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::freshon-invoices/*"
  }]
}

Rules

  • No long-lived access keys for workloads: give EC2, ECS and Lambda instance/task roles; CI uses OIDC (chapter 121).
  • Least privilege: specific actions on specific resources, never "Action": "*" for an app.
  • Humans: SSO with MFA; no daily use of the root account (lock it away, with MFA).
  • Separate accounts or projects for prod and dev: the strongest boundary there is.
  • Audit with CloudTrail and IAM Access Analyzer; remove unused permissions.

Practice

132.1 basic Write a least-privilege IAM policy that lets a service put and get objects only under invoices/ in one bucket.

Allow s3:PutObject and s3:GetObject on arn:aws:s3:::bucket/invoices/*; add s3:ListBucket on the bucket with a s3:prefix condition only if listing is needed.
