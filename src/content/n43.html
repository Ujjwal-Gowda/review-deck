Git's model: three places your changes live, and the commands that move them between those places.

The three areas

working tree ──git add──► staging area (index) ──git commit──► repository (.git) your files (choose what goes (permanent snapshots, on disk in the next snapshot) each with an ID) ◄──────────── git restore ◄─────────── ◄── git restore --staged ──

A commit is a snapshot of the whole project (not a diff), plus metadata: author, date, message, and a pointer to its parent commit(s). Its ID is a SHA hash of all of that, so history can't be changed silently. HEAD means "the commit you're on now", usually via a branch name.

Setup, once

git config --global user.name "Ujjwal"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --global pull.rebase true           # keep history linear when pulling
git config --global core.editor "code --wait"  # or nano / vim

The everyday loop

git init                         # or: git clone <url>
git status                       # ALWAYS know where you are
git diff                         # unstaged changes (working tree vs index)
git diff --staged                # what will be committed (index vs HEAD)
git add -p                       # stage hunk by hunk: review your own change as you stage it
git commit -m "Reserve stock when order is placed"
git log --oneline --graph --decorate -20
git show HEAD                    # the last commit's diff
git mv old.py new.py             # rename (keeps history readable)
git rm --cached secrets.env      # stop tracking a file but keep it on disk

Undoing things, from safest to most destructive

SituationCommandDestroys work?
Unstage a filegit restore --staged fno
Fix the last commit's message or add a forgotten filegit commit --amendrewrites the last commit (fine if not yet pushed)
Undo a pushed commitgit revert <sha>no: adds a new inverse commit
Discard edits to a filegit restore fyes: uncommitted edits are gone
Move the branch back but keep the changesgit reset --soft HEAD~1no
Throw away commits AND changesgit reset --hard <sha>yes
"I lost a commit!"git reflog, then git switch -c rescue <sha>the safety net: commits stay recoverable for about 90 days

Good commits

  • One logical change per commit. It should build and pass tests on its own.
  • Messages: an imperative summary under about 72 characters ("Fix negative stock on refund"), a blank line, then why in the body. Many teams use Conventional Commits (feat:, fix:, docs:, refactor:), which tools use to generate changelogs and version bumps.
  • Commit often, push when coherent. You can tidy local history before sharing (chapter 45).
