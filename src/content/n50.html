Contributing to projects you don't own: the workflow, the etiquette, and how to pick a first issue.

The fork workflow

gh repo fork owner/project --clone        # your copy on GitHub + a local clone; 'upstream' remote set
cd project && git switch -c fix/typo-in-readme
# …change, test…
git commit -m "docs: fix install command in README"
git push -u origin fix/typo-in-readme
gh pr create --repo owner/project --fill
git fetch upstream && git rebase upstream/main   # keep your branch current while the PR is open

Before you write code

  1. Read CONTRIBUTING.md, the code of conduct, and a few recently merged PRs. They show the style reviewers expect.
  2. For anything beyond a typo, comment on the issue first ("I'd like to take this; my plan is X"). Maintainers may already have a direction.
  3. Make the test suite run locally before changing anything, so you know failures are yours.

Picking a first contribution

  • Labels: good first issue, help wanted, documentation.
  • Tools you already use are best: you understand the bug. Reproduce it, write a failing test, then fix it.
  • Docs, error messages, tests and small bug fixes are real contributions and get merged fastest.

Etiquette

Maintainers are usually volunteers. Be patient (a week without a reply is normal), keep PRs small, don't argue style, and never ping repeatedly. If a PR is declined, ask what would make it acceptable, or maintain it in your fork.
