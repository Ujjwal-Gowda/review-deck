Resolving conflicts calmly, rewriting local history cleanly, and the power tools.

Merge conflicts

A conflict happens when both sides changed the same lines (or one side edited a file the other deleted). Git stops and marks the file:

<<<<<<< HEAD
const DELIVERY_FEE = 3000;
=======
const DELIVERY_FEE = calcFee(zone);
>>>>>>> feature/zone-fees
  1. git status lists the conflicted files.
  2. Edit each one to the correct combined result (not just "mine" or "theirs"), and delete the markers.
  3. Run the tests. A clean merge can still be semantically wrong.
  4. git add file, then git merge --continue (or git rebase --continue). To bail out: git merge --abort.

Tip: git config --global merge.conflictstyle zdiff3 also shows the common ancestor, which makes it much easier to see what each side intended.

Rebase: replay your commits on a new base

before: A ── B ── C ◄── main after `git rebase main` on feature: \ A ── B ── C ── D' ── E' ◄── feature D ── E ◄── feature (new commits, new SHAs, linear history)
git switch feature
git fetch origin
git rebase origin/main           # update your branch on top of the latest main
The golden rule

Never rebase commits that others have already pulled. Rebasing creates new commits, and anyone who built on the old ones gets a tangled history. Rebase your own unpushed or personal branch freely; if you must update an already-pushed PR branch, use git push --force-with-lease, which refuses if someone else pushed in the meantime.

Interactive rebase: tidy up before sharing

git rebase -i HEAD~4       # opens an editor listing the last 4 commits:
# pick   a1b2 Add stock reservation
# squash c3d4 fix typo              ← fold into the previous commit
# reword e5f6 wip                   ← change the message
# drop   g7h8 debug prints          ← delete the commit
git commit --fixup a1b2  &&  git rebase -i --autosquash main    # mark fixups as you go; squash them automatically

Trade-offs: merge vs rebase

Merge: preserves exactly what happened and is safe on shared branches, but history gets noisy with merge commits. Rebase: a clean linear history that's easy to bisect and read, but it rewrites commits, so use it only on your own branches. A common team setup: rebase your feature branch locally, then "squash and merge" or "rebase and merge" the PR on GitHub.

45.1 think Create a conflict on purpose (edit the same line on two branches), resolve it with a merge, reset, then resolve it with a rebase. Compare the two graphs.

The merge leaves a merge commit containing the resolution; the rebase leaves a linear history where your commit's diff includes the resolution. git reset --hard ORIG_HEAD undoes a finished merge or rebase so you can retry.
