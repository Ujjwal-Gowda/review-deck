Binary search is more than "find x in a sorted list". It's a way to answer any yes/no question whose answer flips only once.

Linear vs binary

Linear search checks every item: O(n), and works on anything. Binary search halves a sorted range each step: O(log n). A million items take about 20 steps.

The template that doesn't have off-by-one bugs

def lower_bound(a, target):
    """First index i with a[i] >= target (len(a) if there's none)."""
    lo, hi = 0, len(a)              # the answer is always in [lo, hi]
    while lo < hi:
        mid = (lo + hi) // 2
        if a[mid] < target:
            lo = mid + 1            # the answer is to the right of mid
        else:
            hi = mid                # mid might be the answer; keep it
    return lo
# contains(a, t):   i = lower_bound(a, t); return i < len(a) and a[i] == t
# upper_bound: first index with a[i] > target (change < to <=).   count of t = upper − lower.

Python's bisect.bisect_left is exactly this. Go has sort.Search / slices.BinarySearch; Rust has slice.binary_search / partition_point; C has bsearch.

Binary search on the answer

If "is capacity c enough?" is false for small c and true from some point on, binary-search the smallest c that works:

def min_van_capacity(orders_kg, vans):
    def fits(cap):                               # can `vans` vans carry the orders IN ORDER with this capacity?
        used, load = 1, 0
        for w in orders_kg:
            if load + w > cap: used, load = used + 1, 0
            load += w
        return used <= vans
    lo, hi = max(orders_kg), sum(orders_kg)      # the answer lies between these
    while lo < hi:
        mid = (lo + hi) // 2
        if fits(mid): hi = mid
        else: lo = mid + 1
    return lo

The same pattern answers: the minimum speed to finish in time, the largest square that fits, the first bad commit (git bisect), and the lowest price at which demand drops. Look for a monotonic yes/no question.
