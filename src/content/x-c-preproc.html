#define BAD_SQUARE(x) x * x
BAD_SQUARE(1 + 2)        /* expands to 1 + 2 * 1 + 2 = 5, not 9 */
SQUARE(i++)              /* i++ evaluated TWICE: undefined behaviour */

Undefined behaviour (UB)

For these operations the C standard says anything may happen, and optimising compilers assume they never occur, which can delete your safety checks.

UBExampleInstead
signed integer overflowINT_MAX + 1check before, use wider types, or __builtin_add_overflow
out-of-bounds accessa[len]track lengths; check bounds
null / dangling pointer dereference*p after free(p)set to NULL; clear ownership rules
uninitialised readsint x; printf("%d", x);always initialise
modifying a string literalchar *s = "hi"; s[0] = 'H';char s[] = "hi";
shifting too far / negative values1 << 32, -1 << 1unsigned types, and checks
unsequenced modificationsi = i++ + 1one side effect per statement
strict aliasing violationsreading a float through an int *memcpy between types
data racestwo threads writing unsynchronisedmutexes and atomics

Your safety net

gcc -std=c17 -Wall -Wextra -Wpedantic -Wshadow -Wconversion -g \
    -fsanitize=address,undefined -fno-omit-frame-pointer main.c   # development builds
gcc -O2 -D_FORTIFY_SOURCE=2 -fstack-protector-strong main.c       # hardened release builds
clang-tidy main.c; cppcheck .                                     # static analysis

This is exactly the class of bug Rust's compiler rules out, and why so much new systems code is written in Rust. Knowing C's UB makes you appreciate, and understand, what safe languages do for you (Rust Ownership).

0.1 think Why might if (x + 1 < x) handle_overflow(); (with int x) be deleted entirely by gcc -O2? Demonstrate it and write a correct check.

Signed overflow is UB, so the compiler may assume x + 1 < x is never true and remove the branch. Correct: if (x == INT_MAX) before adding, or if (__builtin_add_overflow(x, 1, &r)). -fsanitize=undefined reports the overflow at runtime.
