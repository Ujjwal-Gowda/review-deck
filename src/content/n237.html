Project 3: Full-Stack Real-Time Order Engine. Build a resilient end-to-end commerce system with React, TypeScript, PostgreSQL, and Redis.

The Real World of Full-Stack Architecture

Toy full-stack apps work fine when you are the only user clicking buttons on localhost. But real production systems operate in a hostile world of unstable mobile networks, concurrent flash sales, server restarts, and stale client state. If two users click "Buy Now" on the last remaining vintage sneaker at the exact same millisecond, a naive app sells both, creates negative inventory, and triggers an operational nightmare.

In this capstone, you will construct FreshPulse: a high-throughput, real-time order dashboard and checkout engine. You will eliminate race conditions in the database, implement optimistic UI state with instant rollback, and stream live order mutations via Redis Pub/Sub and Server-Sent Events (SSE).

Phase 1: The Race-Proof Database Core

The most dangerous bug in web development is the Check-Then-Act race condition (Time of Check to Time of Use, or TOCTOU). Never write this in your backend:

// [FAIL] CRITICAL BUG: Catastrophic race condition under concurrent traffic
const product = await db.query("SELECT stock FROM products WHERE id = $1", [productId]);
if (product.stock >= quantity) {
  // If 5 requests reach this line before any UPDATE executes, ALL 5 succeed!
  await db.query("UPDATE products SET stock = stock - $1 WHERE id = $2", [quantity, productId]);
  await db.query("INSERT INTO orders (...) VALUES (...)");
}

Instead, use PostgreSQL's atomic guarantees. You have two robust architectural options:

Approach A: Atomic Conditional Update (Fastest)

Execute single-statement atomic decrement with a conditional predicate:

UPDATE products
SET stock = stock - $1, updated_at = NOW()
WHERE id = $2 AND stock >= $1
RETURNING id, name, stock;

If rowCount === 0, the product was out of stock. The database engine guarantees single-thread serialization per row on writes.

Approach B: Explicit Pessimistic Row Lock

For complex checkouts (multi-item orders, bundled discounts), lock rows inside a transaction:

BEGIN;
-- Lock only the targeted product rows in strict ID order to avoid deadlocks
SELECT id, stock FROM products 
WHERE id IN ($1, $2) 
ORDER BY id 
FOR UPDATE;

-- All other transactions wanting these items wait here until COMMIT
...
COMMIT;

Phase 2: The Resilient Express + Redis Backend

Here is the production-grade order service handling idempotency, transactions, cache invalidation, and real-time broadcasting:

import { Router, Request, Response } from "express";
import { z } from "zod";
import { pool } from "../db";
import { redisClient, redisPublisher } from "../redis";

export const orderRouter = Router();

const CreateOrderSchema = z.object({
  idempotencyKey: z.string().uuid(),
  items: z.array(z.object({
    productId: z.string().uuid(),
    quantity: z.number().int().positive().max(50),
  })).nonempty(),
  customerEmail: z.string().email(),
});

orderRouter.post("/orders", async (req: Request, res: Response) => {
  const parseResult = CreateOrderSchema.safeParse(req.body);
  if (!parseResult.success) {
    res.status(422).json({ error: "Validation failed", details: parseResult.error.flatten() });
    return;
  }

  const { idempotencyKey, items, customerEmail } = parseResult.data;
  
  // 1. Check Idempotency Cache to prevent duplicate double-charges on network retries
  const cachedResponse = await redisClient.get(`idempotency:${idempotencyKey}`);
  if (cachedResponse) {
    res.status(200).json(JSON.parse(cachedResponse));
    return;
  }

  const client = await pool.connect();
  try {
    await client.query("BEGIN");

    // 2. Lock and decrement stock for all items
    let totalAmountCents = 0;
    const reservedItems: Array<{ id: string; name: string; priceCents: number; quantity: number }> = [];

    // Sort item IDs to guarantee deterministic lock acquisition order (prevents deadlocks!)
    const sortedItems = [...items].sort((a, b) => a.productId.localeCompare(b.productId));

    for (const item of sortedItems) {
      const updateRes = await client.query(
        `UPDATE products 
         SET stock = stock - $1 
         WHERE id = $2 AND stock >= $1 
         RETURNING id, name, price_cents, stock`,
        [item.quantity, item.productId]
      );

      if (updateRes.rowCount === 0) {
        await client.query("ROLLBACK");
        res.status(409).json({ 
          error: "INSUFFICIENT_STOCK", 
          message: `Item ${item.productId} is out of stock or requested quantity unavailable.` 
        });
        return;
      }

      const prod = updateRes.rows[0];
      totalAmountCents += prod.price_cents * item.quantity;
      reservedItems.push({ id: prod.id, name: prod.name, priceCents: prod.price_cents, quantity: item.quantity });
    }

    // 3. Create Order Record
    const orderRes = await client.query(
      `INSERT INTO orders (idempotency_key, customer_email, total_cents, status) 
       VALUES ($1, $2, $3, 'CONFIRMED') 
       RETURNING id, created_at`,
      [idempotencyKey, customerEmail, totalAmountCents]
    );
    const orderId = orderRes.rows[0].id;

    for (const item of reservedItems) {
      await client.query(
        `INSERT INTO order_items (order_id, product_id, quantity, unit_price_cents) 
         VALUES ($1, $2, $3, $4)`,
        [orderId, item.id, item.quantity, item.priceCents]
      );
    }

    await client.query("COMMIT");

    const payload = {
      orderId,
      status: "CONFIRMED",
      totalAmountCents,
      items: reservedItems,
      createdAt: orderRes.rows[0].created_at,
    };

    // 4. Save Idempotency Cache (24 hour TTL)
    await redisClient.setEx(`idempotency:${idempotencyKey}`, 86400, JSON.stringify(payload));

    // 5. Invalidate Product Cache & Broadcast Event to Live Dashboards
    await redisPublisher.publish("live-orders", JSON.stringify({ type: "ORDER_CREATED", payload }));

    res.status(201).json(payload);
  } catch (err) {
    await client.query("ROLLBACK");
    console.error("Order placement failed:", err);
    res.status(500).json({ error: "INTERNAL_SERVER_ERROR" });
  } finally {
    client.release();
  }
});

Phase 3: Real-Time Updates with Server-Sent Events (SSE)

Why choose SSE over WebSockets for live order updates?

  • Transport Simplicity: SSE runs over standard HTTP/2 streams. No custom WebSocket handshakes, no firewall proxy blockades.
  • Built-in Reconnection: If the Wi-Fi drops, the browser's native EventSource automatically reconnects and sends a Last-Event-ID header so the server can backfill missed events.
  • Battery & Memory: Mono-directional streaming uses minimal system overhead compared to full-duplex socket state management.
import { Router } from "express";
import { redisSubscriber } from "../redis";

export const sseRouter = Router();

// Track all active HTTP response streams
const activeClients = new Set<Response>();

redisSubscriber.subscribe("live-orders", (message) => {
  const eventPayload = `event: order_update\ndata: ${message}\n\n`;
  for (const client of activeClients) {
    client.write(eventPayload);
  }
});

sseRouter.get("/orders/stream", (req, res) => {
  // Required SSE Headers
  res.writeHead(200, {
    "Content-Type": "text/event-stream",
    "Cache-Control": "no-cache, no-transform",
    "Connection": "keep-alive",
    "X-Accel-Buffering": "no", // Disable proxy buffering for Nginx
  });

  res.write(`event: connected\ndata: {"status":"streaming"}\n\n`);
  activeClients.add(res);

  // Heartbeat keep-alive every 15 seconds to prevent intermediate proxy timeouts
  const heartbeat = setInterval(() => {
    res.write(": heartbeat\n\n");
  }, 15000);

  req.on("close", () => {
    clearInterval(heartbeat);
    activeClients.delete(res);
  });
});

Phase 4: React 19 Frontend with Optimistic State & Live Sync

The client needs to feel instantaneous. When a manager modifies order status or a customer buys an item, update the UI immediately with TanStack Query. If the network drops or the server rejects the transaction, rollback the UI state cleanly and alert the user.

import React, { useEffect } from "react";
import { useQuery, useMutation, useQueryClient } from "@tanstack/react-query";

interface Order {
  orderId: string;
  customerEmail: string;
  totalAmountCents: number;
  status: "PENDING" | "CONFIRMED" | "CANCELLED";
}

export function LiveOrderDashboard() {
  const queryClient = useQueryClient();

  // 1. Primary Data Query
  const { data: orders = [], isLoading } = useQuery<Order[]>({
    queryKey: ["orders"],
    queryFn: async () => {
      const res = await fetch("/api/v1/orders");
      if (!res.ok) throw new Error("Failed to fetch orders");
      return res.json();
    },
  });

  // 2. Server-Sent Events listener updating the React Query Cache
  useEffect(() => {
    const eventSource = new EventSource("/api/v1/orders/stream");

    eventSource.addEventListener("order_update", (event) => {
      const data = JSON.parse(event.data);
      if (data.type === "ORDER_CREATED") {
        queryClient.setQueryData<Order[]>(["orders"], (old = []) => [data.payload, ...old]);
      }
    });

    eventSource.onerror = () => {
      console.warn("SSE connection lost. Browser will auto-reconnect...");
    };

    return () => eventSource.close();
  }, [queryClient]);

  // 3. Optimistic Mutation for cancelling an order
  const cancelMutation = useMutation({
    mutationFn: async (orderId: string) => {
      const res = await fetch(`/api/v1/orders/${orderId}/cancel`, { method: "POST" });
      if (!res.ok) throw new Error("Failed to cancel order");
      return res.json();
    },
    onMutate: async (orderId) => {
      // Cancel outgoing refetches so they don't overwrite our optimistic update
      await queryClient.cancelQueries({ queryKey: ["orders"] });
      const previousOrders = queryClient.getQueryData<Order[]>(["orders"]);

      // Optimistically update cache immediately
      queryClient.setQueryData<Order[]>(["orders"], (old = []) =>
        old.map((o) => (o.orderId === orderId ? { ...o, status: "CANCELLED" } : o))
      );

      // Return context with previous snapshot
      return { previousOrders };
    },
    onError: (err, orderId, context) => {
      // Rollback to previous state if API call failed
      if (context?.previousOrders) {
        queryClient.setQueryData(["orders"], context.previousOrders);
      }
      alert(`Could not cancel order: ${err.message}`);
    },
    onSettled: () => {
      // Always sync with database state afterwards
      queryClient.invalidateQueries({ queryKey: ["orders"] });
    },
  });

  if (isLoading) return <div className="p-4">Loading active order ledger...</div>;

  return (
    <div className="order-dashboard">
      <h2>Live Dispatch Board ({orders.length} orders)</h2>
      <div className="order-grid">
        {orders.map((order) => (
          <div key={order.orderId} className={`order-card status-${order.status.toLowerCase()}`}>
            <div className="header">
              <span className="id">#{order.orderId.slice(0, 8)}</span>
              <span className="badge">{order.status}</span>
            </div>
            <p className="email">{order.customerEmail}</p>
            <p className="price">${(order.totalAmountCents / 100).toFixed(2)}</p>
            {order.status === "CONFIRMED" && (
              <button onClick={() => cancelMutation.mutate(order.orderId)}>
                Cancel Order
              </button>
            )}
          </div>
        ))}
      </div>
    </div>
  );
}

Drill: Deadlock Prevention in Multi-Item Orders (Click to expand)

Scenario: User 1 orders Item A and Item B simultaneously as User 2 orders Item B and Item A.

If Transaction 1 locks Row A and waits for Row B, while Transaction 2 locks Row B and waits for Row A, PostgreSQL detects a deadlock and kills one of the transactions with error code 40P01.

Question: How did our implementation prevent this deadlock with a single line of code?

Answer: We sorted the requested item IDs lexicographically before acquiring locks:

const sortedItems = [...items].sort((a, b) => a.productId.localeCompare(b.productId));

When all concurrent transactions acquire row locks in the exact same deterministic global order (e.g. always lock UUID 02a... before UUID f7b...), circular lock dependencies are mathematically impossible!
