Everything that changes between environments (dev, staging, production) lives outside the code.

What counts as configuration

Database URLs, API keys, ports, feature flags, log levels, third-party endpoints, timeouts. The test: could you open-source the code right now without leaking anything? If not, config (or secrets) are mixed into the code.

12-factor config: environment variables

# .env: local development only; it's in .gitignore. Commit a .env.example with dummy values instead.
DATABASE_URL=postgres://dev:dev@localhost:5432/shop
PORT=8080
LOG_LEVEL=debug
FEATURE_NEW_CHECKOUT=true

Load once, validate at startup, fail fast

import { z } from "zod";
const Env = z.object({
  DATABASE_URL: z.string().url(),
  PORT: z.coerce.number().int().default(8080),
  LOG_LEVEL: z.enum(["debug", "info", "warn", "error"]).default("info"),
});
export const config = Env.parse(process.env);   // crashes at boot with a clear message, not at 3 a.m. on first use
from pydantic_settings import BaseSettings
class Settings(BaseSettings):
    database_url: str
    port: int = 8080
    log_level: str = "info"
settings = Settings()        # reads the env (and .env); raises if database_url is missing
type Config struct { DatabaseURL string; Port int }
func Load() (Config, error) {
    c := Config{DatabaseURL: os.Getenv("DATABASE_URL"), Port: 8080}
    if c.DatabaseURL == "" { return c, errors.New("DATABASE_URL is required") }
    if p := os.Getenv("PORT"); p != "" {
        n, err := strconv.Atoi(p); if err != nil { return c, fmt.Errorf("PORT: %w", err) }
        c.Port = n
    }
    return c, nil
}

Precedence (lowest to highest)

Built-in defaults, then a config file, then environment variables, then command-line flags. Every serious tool follows this order (git, docker, kubectl) so an operator can override anything without editing files.

Secrets are special configuration

  • Never commit them; add a secret scanner (gitleaks, GitHub push protection).
  • In production, inject them from a secret manager (AWS Secrets Manager, Vault, Doppler, Kubernetes Secrets, GitHub Actions secrets).
  • Never log them or send them in error messages; rotate them if they're ever exposed.

Feature flags

These are runtime switches (if flags.new_checkout:) that let you deploy code "dark" and turn it on for 5% of users, or instantly off if it breaks. They separate deploy from release. The cost: stale flags become technical debt, so delete them once a feature is fully rolled out.

40.1 basic Take one of your existing projects, find every hard-coded URL, key or port, and move them to validated env config with a .env.example.

Search with rg -n "http(s)?://|api[_-]?key|localhost:|password" --glob '!node_modules', then centralise everything in one config module that's loaded at startup.
