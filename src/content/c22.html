Memory moves in cache lines (64 bytes). Reading array elements in order is fast, because each line brings in the next several items and the prefetcher predicts what's coming. Chasing pointers through scattered objects causes cache misses that are about 100× slower. This locality is why arrays beat linked lists, why "structure of arrays" layouts exist in games and ML, and why NumPy (contiguous C arrays) is about 50× faster than Python lists of objects.

Other hardware realities: branch prediction (unpredictable ifs in hot loops are costly), SIMD (one instruction processes 4–16 numbers at once), multicore (parallelism, chapter 20), and GPUs (thousands of simple cores; chapter 28).

Performance workflow

  1. Make it work, make it right, then make it fast, and only where it's needed. "Premature optimisation is the root of all evil" (Knuth).
  2. Measure: profile to find the hotspot (it's rarely where you'd guess). Tools: cProfile, py-spy, perf, Chrome DevTools, pprof, flame graphs.
  3. Fix in order of leverage: a better algorithm or data structure (100–1000×), then fewer I/O round trips (batch queries, add caching), then better memory layout and less allocation, then micro-optimisations last.
  4. Benchmark before and after, on realistic data.

Latency is the time for one operation. Throughput is operations per second. They're different goals: batching raises throughput but can raise latency. Caching is the universal speed trick, but "there are only two hard things in computer science: cache invalidation and naming things."

Practice

5.1 basic Run python3 -c "import dis; dis.dis(lambda x: x*2+1)" and gcc -O2 -S on the equivalent C function. Compare the bytecode with the assembly.

Python shows stack-machine bytecode (LOAD_FAST, BINARY_OP, RETURN_VALUE) interpreted at runtime. GCC emits 1–2 real CPU instructions (e.g. lea eax, [rdi+rdi+1]). That's the interpreter-vs-compiler gap in miniature.
