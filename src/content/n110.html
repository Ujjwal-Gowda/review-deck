Finding out how a system behaves under load before your users do.

// k6 script: k6 run load.js
import http from "k6/http"; import { check, sleep } from "k6";
export const options = {
  stages: [{ duration: "1m", target: 50 }, { duration: "3m", target: 50 }, { duration: "1m", target: 0 }],  // ramp, hold, down
  thresholds: { http_req_duration: ["p(95)<300"], http_req_failed: ["rate<0.01"] },                   // pass/fail criteria
};
export default function () {
  const r = http.get("https://staging.api/orders?limit=20");
  check(r, { "200": x => x.status === 200 });
  sleep(1);                                                          // think time between actions
}

Reading the results

  • Percentiles, not averages: p50 is the typical user; p95/p99 are the unlucky ones. An average of 80 ms can hide a p99 of 4 s.
  • Throughput (requests per second) rises with load until it saturates. After that, latency climbs steeply: that knee is your capacity.
  • Little's law: concurrent requests = throughput × latency. At 200 req/s and 0.5 s latency, 100 requests are in flight, so you need a pool that big.

Test against staging with production-like data volumes, from a machine that isn't the bottleneck itself, and watch the server's metrics (CPU, DB, pools) during the run. Other tools: Locust (Python), Gatling, vegeta, oha.

Practice

110.1 basic Load-test a local API with k6 at 10, 50 and 100 virtual users. Plot p95 latency against throughput and find the knee.

Throughput rises, then flattens, while p95 shoots up: that point is capacity. Note the server CPU, database and pool usage at that moment to find the bottleneck.
