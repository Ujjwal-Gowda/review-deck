Running containers in production: secure, observable and well-behaved.

AreaPractice
Securitynon-root USER; read-only root filesystem (--read-only + a tmpfs for /tmp); drop capabilities (--cap-drop ALL); no --privileged; minimal or distroless base; scan images in CI; never mount the Docker socket into app containers
Resourcesset memory and CPU limits (--memory 512m --cpus 1). Without limits, one leaky container can OOM the whole host. Runtimes should respect them (Node --max-old-space-size, JVM container awareness).
Healtha HEALTHCHECK or orchestrator probes; restart policies (unless-stopped)
Signalsexec-form CMD so the app is PID 1 and gets SIGTERM; or --init (tini) to reap zombies; handle graceful shutdown within the stop timeout
Loggingwrite to stdout/stderr (the runtime collects it); set log rotation (--log-opt max-size=10m) or the logs fill the disk
Configenv vars and secrets injected at runtime; the same image in every environment (build once, promote everywhere)
Statelessnessstate in volumes, DBs or object storage, so containers can be killed and replaced at any time
TimeUTC everywhere; the image timezone doesn't matter if you store UTC

Practice

119.1 basic Run a container with --read-only --cap-drop ALL --user 1000 --memory 256m. What breaks, and how do you fix it properly?

Writes to /tmp or caches fail: mount a --tmpfs /tmp. Binding ports below 1024 fails: listen on 8080. Out-of-memory kills show up in docker inspect as OOMKilled.
