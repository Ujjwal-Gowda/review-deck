Doing many things at once correctly. The hardest bugs in programming live here.

Concurrency means dealing with many things at once: tasks interleave, possibly on one core. Parallelism means doing many things at once, on multiple cores simultaneously. A single waiter serving ten tables is concurrent; ten waiters are parallel.

I/O-bound vs CPU-bound

I/O-bound work mostly waits on the network or disk (web requests, DB queries). Concurrency helps because you wait on many things at once: use async or threads. CPU-bound work mostly computes (image processing, rendering video frames). Only parallelism across cores helps: use processes, or threads in languages without a GIL. Your Remotion renders use multiple Chrome processes for exactly this reason.

The race condition

import threading
count = 0
def work():
    global count
    for _ in range(100_000):
        count += 1      # NOT atomic: read count → add 1 → write back. Two threads can interleave:
                        # A reads 5, B reads 5, A writes 6, B writes 6 → one increment lost
ts = [threading.Thread(target=work) for _ in range(4)]
for t in ts: t.start()
for t in ts: t.join()
print(count)            # may be less than 400000

lock = threading.Lock()
def safe_work():
    global count
    for _ in range(100_000):
        with lock:      # MUTUAL EXCLUSION: one thread in this "critical section" at a time
            count += 1

A data race is two threads accessing the same memory, at least one of them writing, without synchronisation. The results depend on timing, so the bugs are intermittent and nearly impossible to reproduce. Rust's "sharing XOR mutation" rule (chapter 10) makes data races a compile error.

Synchronisation primitives and hazards

TermMeaning

Safer models: share by communicating

"Don't communicate by sharing memory; share memory by communicating" (Go). Pass messages through channels/queues so each piece of data has one owner at a time. The actor model (Erlang, Akka) works the same way: actors own state and exchange messages.

results := make(chan int)
for _, url := range urls {
    go func(u string) { results <- fetchSize(u) }(url)   // goroutine per URL
}
total := 0
for range urls { total += <-results }                     // collect results; no locks needed

Async / await and the event loop

A single thread runs an event loop. When a task hits await on I/O, it yields and the loop runs another ready task. That's how Node.js serves thousands of connections on one thread.

import asyncio
async def fetch(i):
    await asyncio.sleep(1)          # stands in for a network call; yields to the loop
    return i
async def main():
    results = await asyncio.gather(*(fetch(i) for i in range(100)))   # ~1 second total, not 100
asyncio.run(main())
Async pitfalls

One blocking call (time.sleep, heavy CPU work, synchronous file I/O) inside async code freezes everything. Async is "contagious": a function that awaits must itself be async (the "function colouring" problem). Always add timeouts.

Python's GIL (Global Interpreter Lock) means only one thread runs Python bytecode at a time in CPython, so threads help with I/O but not with CPU work. Use multiprocessing/ProcessPoolExecutor for CPU work (Python 3.13 has an experimental free-threaded build). Go, Rust, Java and C# threads run truly in parallel. JS is single-threaded, with Web Workers and worker_threads for parallel work.

Trade-offs

Threads + locks: flexible and familiar, but races and deadlocks are easy to cause. Message passing: much easier to reason about, at the cost of some copying overhead. Async: huge I/O concurrency on little memory, but code colouring and blocking pitfalls. Processes: real isolation and parallelism, but heavy, with serialisation costs. Default: avoid shared mutable state; use a pool or queue; reach for locks last.
