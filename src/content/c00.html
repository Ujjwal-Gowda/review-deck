Why the skill fades, and the rules that rebuild it.

Why it feels like you're losing it

Programming skill is not knowledge of syntax. It is three things:

  1. A mental model of the machine: what happens to memory when this line runs.
  2. Decomposition: turning a vague goal into small, precise steps.
  3. Debugging: noticing the gap between what you expected and what happened, and closing it.

All three are built by struggle, the uncomfortable minutes where you don't yet know the answer. Psychologists call this "desirable difficulty": effortful retrieval is what writes things into long-term memory. When AI produces the code, you skip exactly the part that builds the skill. You still recognise good code (recognition is easy), but you can no longer produce it (recall is hard). That gap is the feeling you described.

The rules for this guide

The seven rules
  1. No AI for the exercises. Use AI afterwards to review your solution, never before to produce it.
  2. Type every example; don't copy-paste. Your fingers learn syntax. Then change something and predict the result before running.
  3. Predict, then run. Before running any code, say out loud (or write) what it will print. A wrong prediction is the most valuable thing that can happen, because it shows exactly where your model is broken.
  4. The 20-minute rule. Stuck? Struggle for 20 minutes: re-read, print things, draw memory. Then look at docs. Then the solution. Then close the solution and re-write it from memory the next day.
  5. Read the official docs. python3 -c "help(str.split)", man 3 printf, go doc strings.Split, docs.python.org, MDN, doc.rust-lang.org. Reading docs is a core skill that AI has let atrophy.
  6. Draw memory. Boxes and arrows on paper: variables, what they point to, the call stack. Every senior engineer does this in their head. Start by doing it on paper.
  7. Spaced repetition. Re-do old exercises from scratch after 1 day, 1 week and 1 month. If you can't, you didn't learn it; you recognised it.
Rule 8: never learn a tool without building something that breaks

Don't learn Docker by reading "what is Docker". Build a Node API, then add Postgres, then hit "works on my machine", then containerise it, hit a networking problem, learn Docker networking, lose your data, learn volumes, and finally reach for Compose. Each tool in this curriculum is introduced as the answer to a problem you've just run into.

How to use AI correctly from now on

Instead of…Do…
"Write a function that does X"Write it yourself, then: "Review this. Don't rewrite it; list bugs and edge cases I missed."
"Fix this error"Read the traceback yourself first and form a hypothesis. Then: "My hypothesis is Y. Am I right? Explain, don't fix."
"Explain this code"Explain it yourself first in writing, then ask AI to grade your explanation.
Accepting generated code you can't explainNever merge a line you couldn't have written. If you can't explain it, that's today's lesson.
