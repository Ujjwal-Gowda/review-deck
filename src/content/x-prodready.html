One checklist for "is this service ready for real users?", pulling together the production skills spread across the curriculum.

AreaReady meansChapters
Configurationall config from the environment, validated at startup; same artifact in every environmentConfiguration
Secretsin a secret manager, never in git or logs; rotatableSecrets Management
Health and lifecycleliveness/readiness endpoints; graceful shutdown on SIGTERM; fast startupHealth Checks & Graceful Shutdown
Observabilitystructured logs with request IDs; RED metrics; tracing; dashboardsLogging, Metrics, Tracing
AlertingSLOs defined; burn-rate alerts; every alert has a runbookSLOs, Alerting

Async workqueues and background workers for slow tasks; idempotent consumers; dead-letter queuesQueues, Background Jobs
Correctness under retriesidempotency keys on writes; outbox for eventsAPI Design, Distributed Queues

Data safetyzero-downtime migrations; automated backups with tested restores; disaster-recovery plan with RPO/RTOMigrations, Backups, Disaster Recovery
DeliveryCI gates; automated deploys; canary or rolling release; one-click rollback; feature flagsThe Path to Production, Deployment Strategies
Securitythreat model done; auth and authorisation tested; dependencies scanned; least privilegeSecurity Across the Stack
Operationsan owner, on-call, runbooks, incident processOperating a Service, Incident Response

Use it as a launch review: go row by row, mark each ✓, ✗ or "accepted risk", and give every ✗ an owner and a date. Google calls this a Production Readiness Review.

Practice

0.1 basic Run this checklist against one of your real projects (the printer doctor or the Floor TV app). How many rows pass?

Most personal projects pass configuration and not much else. Pick the three cheapest ✗ rows (usually a health endpoint, structured logs, and a timeout on every network call) and fix them this week.
