Caching strategies, and the ways caches go wrong.

StrategyHowTrade-off
Cache-aside (lazy)the app reads the cache; on a miss, reads the DB and fills the cachethe default; the first read is slow; data is stale until the TTL expires or it's invalidated
Read-throughthe cache library loads from the DB itself on a misscleaner code; same staleness
Write-throughwrite to the cache and the DB togetherthe cache is always fresh; slower writes
Write-back (write-behind)write to the cache, flush to the DB laterfast writes; risk of losing data
Write-aroundwrite only to the DB; cache on readavoids caching data that's never read

Failure modes

ProblemFix
Stale datadelete the key when the data is written (invalidate rather than update, to avoid races) plus a TTL as a safety net
Stampede: a hot key expires and 1,000 requests hit the DB at oncea lock or single-flight per key; serve stale while revalidating; jitter the TTLs
Penetration: repeated lookups for keys that don't existcache "not found" briefly; Bloom filter
Avalanche: many keys expire at once, or the cache restarts emptyrandom TTLs; warm the cache up; replicated cache
Hot keya local in-process cache in front of Redis; replicate the key

Caching layers, from the client inwards: browser (HTTP headers), CDN, reverse proxy, application memory, Redis, database buffer cache. Cache as close to the user as correctness allows. And measure the hit rate: a 30% hit rate is mostly overhead.

Practice

182.1 basic Add cache-aside with Redis to a slow endpoint, then simulate a stampede with 200 concurrent requests right after expiry. Fix it with a per-key lock.

Without the fix, the database sees ~200 identical queries; with single-flight (SET lock NX, others wait briefly and re-read), it sees 1. Add jitter to the TTLs too.
