The single biggest lever on database performance: which indexes to create, and why a query does or doesn't use them.

A B-tree index is a sorted structure (chapter 18) mapping column values to row locations. It turns a full scan (O(n)) into a tree lookup (O(log n)), and also serves ORDER BY and range queries.

CREATE INDEX CONCURRENTLY idx_orders_store_created ON orders (store_id, created_at DESC);  -- CONCURRENTLY: no write lock
-- serves:  WHERE store_id = $1 ORDER BY created_at DESC LIMIT 20      ✓ (leftmost column + sort order)
--          WHERE store_id = $1 AND created_at > $2                   ✓
--          WHERE created_at > $2                                      ✗ (skips the leftmost column)
CREATE INDEX ON orders (customer_id) INCLUDE (total_paise);         -- covering: index-only scans
CREATE INDEX ON orders (created_at) WHERE status = 'pending';       -- partial: small, targeted
CREATE INDEX ON customers (lower(email));                           -- expression index for WHERE lower(email) = …
CREATE INDEX ON products USING gin (tags);                           -- GIN for arrays / jsonb / full-text
CREATE UNIQUE INDEX ON users (phone);                                -- also enforces uniqueness

Why an index isn't used

  • A function or cast on the column: WHERE date(created_at) = … (use a range, or an expression index).
  • Leading wildcards: LIKE '%paneer' (use pg_trgm GIN).
  • Low selectivity: if 60% of rows match, a sequential scan really is faster.
  • A type mismatch between the parameter and the column; stale statistics (run ANALYZE).

The cost of indexes

Every index slows INSERT/UPDATE, uses disk and RAM, and needs vacuuming. Index for real queries: find them with pg_stat_statements, and remove unused ones (pg_stat_user_indexes with idx_scan = 0). Always index foreign-key columns you join or delete on.
