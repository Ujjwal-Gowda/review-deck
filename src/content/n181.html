clients (consumer app, POS, rider app, FOS) │ HTTPS / WS ▼ CDN (static, images) ── Load balancer / reverse proxy (TLS, rate limit) │ ┌─────────────────┼──────────────────┐ ▼ ▼ ▼ API (stateless ×N) Realtime gateway (WS) Admin/FOS API │ │ ▲ │ └──► Redis (cache, sessions, pub/sub) ─┘ ▼ Postgres (primary + replica) Object storage (invoices, images) │ outbox ▼ Queue / stream ──► workers (stock sync, SMS, invoices, rider assignment) ──► external APIs (payments, SMS, maps)

Walk the flows

  • Trace each core use case through the diagram: "customer places order" goes client → LB → API → Postgres (transaction + outbox) → queue → assignment worker → realtime gateway → rider app.
  • Mark the source of truth for each piece of data, and which copies are derived (caches, search indexes, read models).
  • Mark sync vs async edges, and what happens when each box fails (chapter 184).
  • Start with the simplest version that meets the requirements; show how it evolves at 10× and 100×.

Tools: excalidraw, draw.io, Mermaid, or the C4 model (context → containers → components) for layered detail.
