The Psychology of High-Severity Outages

During a major production outage (SEV-1), normal human psychology works against effective resolution: adrenaline surges, cognitive tunnels narrow, people rush to make untested changes in panic, and executives demand instant estimates. Uncontrolled incident rooms degenerate into chaos where five engineers type random commands on production servers simultaneously, making the outage worse.

World-class engineering organizations handle outages not through individual heroics, but through rigid command structures inspired by emergency response teams (FEMA / ICS protocols).

Part 2: The 4 Golden Rules of Live Crisis Management

  1. Mitigate Before Diagnosing: If a code rollout occurred 10 minutes ago, do not spend 45 minutes reading the commit diff to find the offending line. Roll back immediately. Restore customer service first, diagnose in staging later.
  2. Maintain Continuous Stakeholder Updates: Publish updates on the status page every 20 minutes like clockwork. Even if the update is "We are actively investigating database connection pool saturation; next update in 20m", regular communication prevents panicked executives and customers from flooding engineers with DMs.
  3. One Voice in the Room: Only the Incident Commander authorizes changes to production. If an engineer proposes running a script, they state: "IC, I propose restarting the Celery worker pool". The IC responds: "Approved" or "Hold".
  4. Preserve the Timeline: The Scribe records every event with UTC timestamps in a live document: 
    14:02 UTC - Automated alert fires: P99 latency > 3000ms
14:05 UTC - Incident declared SEV-1. IC assigned: @maria
14:11 UTC - Tech Lead identifies spike in unindexed query on `orders` table
14:14 UTC - Feature flag `enable_advanced_order_filter` disabled
14:16 UTC - Latency returns to baseline (45ms). Incident mitigated.

Part 3: The Complete Blameless Postmortem Template

A postmortem is not a witch hunt—it is an investment in systemic resilience. If an engineer typed DROP TABLE, the root cause is not "the engineer was careless", but why did the production database allow single-key destructive commands without confirmation or permissions?

# Incident Postmortem: SEV-1 Checkout Outage
**Date:** 2026-10-09  
**Duration:** 28 minutes  
**Impact:** 4,200 users unable to complete checkout; estimated $38,000 lost GMV.  
**Incident Commander:** Maria Sanchez  

## Executive Summary
At 14:02 UTC, an unindexed query introduced in release `v2.14.0` saturated the primary
PostgreSQL connection pool, causing all checkout requests to timeout with HTTP 504.
The incident was mitigated at 14:30 UTC by rolling back the deployment.

## Contributing Factors (The 5 Whys)
1. **Why did checkouts fail?** Connection pool was exhausted.
2. **Why was the pool exhausted?** Queries on `orders(customer_id, created_at)` were performing sequential table scans taking 4.2s per execution.
3. **Why did the query lack an index?** The migration adding the composite index was omitted in the PR.
4. **Why was the missing index not caught in CI?** The staging database had only 200 rows, where sequential scans run in 0.1ms.
5. **Why was there no query timeout?** The connection pool statement timeout was set to `0` (unlimited).

## What Went Well
- Rollback was executed cleanly in 3 minutes once decided.
- Telemetry immediately highlighted the exact offending query via OpenTelemetry spans.

## What Went Badly
- The initial alert took 7 minutes to page due to overly conservative alert thresholds.
- The status page update was delayed by 15 minutes because login credentials were not in 1Password.

Scenario: A company fires an engineer who pushed a bug that caused an outage.

Question: What is the immediate cultural and technical consequence across the remaining engineering team?

Answer: Fear, concealment, and slow shipping!

When engineers know they will be punished for failures:

  1. They hide mistakes, delay reporting incidents, and avoid taking on-call shifts.
  2. They resist shipping improvements or refactoring brittle legacy code out of fear of being blamed for unexpected side effects.
  3. The underlying systemic flaws (poor test suites, lack of staging parity, dangerous raw credentials) remain unfixed, guaranteeing that the exact same disaster will happen again with a different engineer.
