Seven sorting algorithms, each traced on the same small input, so you can see why some are slow and some are fast.

Input for every trace: [5, 2, 8, 1, 9, 3]

1. Bubble sort: swap neighbours that are out of order

pass 1: [2,5,1,8,3,9] the biggest (9) "bubbles" to the end pass 2: [2,1,5,3,8,9] pass 3: [1,2,3,5,8,9] … repeat until a pass makes no swaps. O(n²). Only for learning.

2. Selection sort: find the minimum, put it next

[1 | 2,8,5,9,3] → [1,2 | 8,5,9,3] → [1,2,3 | 5,9,8] → … always O(n²), but minimal swaps

3. Insertion sort: insert each item into the sorted left part

def insertion_sort(a):
    for i in range(1, len(a)):
        x, j = a[i], i - 1
        while j >= 0 and a[j] > x:      # shift bigger items right
            a[j + 1] = a[j]; j -= 1
        a[j + 1] = x
    return a
[5 | 2,8,1,9,3] → [2,5 | 8,1,9,3] → [2,5,8 | 1,9,3] → [1,2,5,8 | 9,3] → [1,2,5,8,9 | 3] → [1,2,3,5,8,9] O(n²) worst case, but O(n) on nearly sorted data: the fastest choice for small arrays (<~20), which is why real sorts use it inside

4. Merge sort: split in half, sort each half, merge

def merge_sort(a):
    if len(a) <= 1: return a
    mid = len(a) // 2
    left, right = merge_sort(a[:mid]), merge_sort(a[mid:])
    out, i, j = [], 0, 0
    while i < len(left) and j < len(right):          # merge: repeatedly take the smaller front item
        if left[i] <= right[j]: out.append(left[i]); i += 1
        else: out.append(right[j]); j += 1
    return out + left[i:] + right[j:]
[5,2,8,1,9,3] [5,2,8] [1,9,3] split: log n levels [5] [2,8] [1] [9,3] [2] [8] [9] [3] [5] [2,8] [1] [3,9] merge back up: O(n) work per level [2,5,8] [1,3,9] [1,2,3,5,8,9] total O(n log n) always; stable; needs O(n) extra memory

5. Quicksort: partition around a pivot

def quicksort(a, lo=0, hi=None):
    if hi is None: hi = len(a) - 1
    if lo >= hi: return a
    pivot, i = a[hi], lo                     # Lomuto partition: everything < pivot goes to the left
    for j in range(lo, hi):
        if a[j] < pivot: a[i], a[j] = a[j], a[i]; i += 1
    a[i], a[hi] = a[hi], a[i]                # the pivot is now in its final place
    quicksort(a, lo, i - 1); quicksort(a, i + 1, hi)
    return a
pivot 3: [2,1 | 3 | 8,9,5] then sort each side. Average O(n log n), in place, very cache-friendly. Worst case O(n²) (already-sorted input with a bad pivot): use a random or median-of-three pivot.

6. Heap sort

Heapify the array (O(n)), then repeatedly pop the max to the end. O(n log n) always, in place, but not stable and less cache-friendly (Heaps).

7. Counting / radix sort: no comparisons at all

def counting_sort(a, max_value):                 # for small integer ranges (ages, ratings 1–5, pin codes)
    counts = [0] * (max_value + 1)
    for x in a: counts[x] += 1
    return [v for v, c in enumerate(counts) for _ in range(c)]   # O(n + k)

Comparison sorts can't beat O(n log n) (Big-O). Counting and radix sort avoid comparing, so they can, but only for integers or other bounded keys.

Stable means items with equal keys keep their original order. It matters when you sort by date and then by store. In practice, call the built-in sort: Python and Java use Timsort (merge + insertion, stable); C++, Go and Rust's unstable sorts use pdqsort/introsort (quicksort + heapsort + insertion).

Practice

0.1 basic Implement insertion, merge and quicksort, and time them on 10,000 random numbers, 10,000 already-sorted numbers, and 10,000 equal numbers.

On sorted input, insertion sort is fast (O(n)) while naive quicksort (last-element pivot) degrades to O(n²) and may hit the recursion limit. Merge sort is steady on all three. Equal elements hurt Lomuto quicksort too: three-way partitioning fixes it.
