Running a secret manager: central storage, access control, auditing and rotation.

aws secretsmanager create-secret --name prod/orders/db --secret-string '{"url":"postgres://…"}'
aws secretsmanager get-secret-value --secret-id prod/orders/db      # only roles allowed by IAM can read it; every read is logged
vault kv put secret/orders/razorpay key_id=… key_secret=…          # HashiCorp Vault
vault read database/creds/orders-app                                # DYNAMIC secret: a fresh DB user that expires in 1 hour
  • Centralise: one place, organised by environment and service, instead of .env files copied between laptops.
  • Inject at runtime: environment variables or mounted files, fetched by the platform (ECS task definitions, External Secrets in Kubernetes, doppler run).
  • Least privilege: each service reads only its own secrets.
  • Rotation: scheduled rotation (the manager updates both the provider and the stored value); apps reload new values without redeploying, or during the next rolling restart.
  • Dynamic, short-lived credentials beat static ones: if one leaks, it's already expired.
  • Audit logs show who read which secret, and when.
