Handling credentials across the software lifecycle without ever leaking them.

StageWhere secrets live
Local dev.env (gitignored) or a secret manager's CLI (doppler run --, op run --)
CIencrypted CI secrets (GitHub Actions secrets and environments); cloud access via OIDC short-lived tokens, not long-lived keys
Runtimea secret manager (AWS Secrets Manager, GCP Secret Manager, Vault, Doppler, Infisical) injected as env vars or files; Kubernetes Secrets (base64 is not encryption, so enable encryption at rest or use external-secrets)

Rules

  • Never commit a secret. Enable GitHub push protection and a pre-commit scanner (gitleaks).
  • If one leaks: rotate it first, then clean up history. Assume it has already been scraped: bots scan GitHub within minutes.
  • Least privilege and scoping: separate keys per environment and service, with the minimum permissions.
  • Short-lived over long-lived: OIDC, IAM roles, workload identity and dynamic database credentials expire automatically.
  • Rotate regularly and design for rotation (accept two valid keys during the switch).
  • Never log secrets, and redact them from error reports.

Worth checking now: the Google API key embedded in the FreshOn demo kit's JS is meant to be public (browser keys always are), which is exactly why it must be restricted by HTTP referrer and API in Google Cloud Console.
