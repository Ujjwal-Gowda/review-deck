What your structs, arrays and strings physically look like in RAM, and why the layout affects speed and correctness.

Addresses and word size

Memory is one enormous byte array; an address is an index into it. On a 64-bit machine, pointers are 8 bytes, so the address space is 2⁶⁴ (in practice 48 bits are used). A word is the CPU's natural unit: 8 bytes, the size of a register.

Alignment and padding

CPUs read memory fastest (and on some architectures, only correctly) when a value's address is a multiple of its size: a 4-byte int at an address divisible by 4, an 8-byte double at one divisible by 8. So compilers insert invisible padding into structs:

struct Bad  { char a; double b; char c; };   // 1 + 7 pad + 8 + 1 + 7 pad = 24 bytes
struct Good { double b; char a; char c; };   // 8 + 1 + 1 + 6 pad          = 16 bytes
printf("%zu %zu\n", sizeof(struct Bad), sizeof(struct Good));   // 24 16
Bad: [a][· · · · · · ·][b b b b b b b b][c][· · · · · · ·] 24 B Good: [b b b b b b b b][a][c][· · · · · ·] 16 B Rule: order fields from largest to smallest.

Rust reorders struct fields automatically for you (unless you write #[repr(C)], which you need when sharing structs with C). C and Go keep your order, so you choose. With a million structs in an array, 24 vs 16 bytes is 8 MB of wasted RAM and cache.

Arrays: contiguous, fixed-stride

int a[5] is 5 × 4 = 20 bytes back to back. Element i is at base + i × sizeof(int), which is why indexing is O(1) and why a bad index silently reads a neighbour in C. A 2-D array int g[3][4] is stored row-major (row 0, then row 1…), so looping row by row walks memory in order (fast), while looping column-first jumps around (cache misses; chapter 5 explains the cost).

for (int r = 0; r < ROWS; r++)        // fast: sequential
    for (int c = 0; c < COLS; c++) sum += g[r][c];
for (int c = 0; c < COLS; c++)        // slow on big arrays: strided
    for (int r = 0; r < ROWS; r++) sum += g[r][c];

Structure of Arrays vs Array of Structures

struct P { float x, y, z, mass; } ps[N];        // AoS: natural, but summing mass loads x,y,z too
struct Ps { float x[N], y[N], z[N], mass[N]; };  // SoA: summing mass streams one tight array (SIMD-friendly)

Games, databases (column stores like ClickHouse) and ML frameworks use SoA layouts for exactly this reason.

Exercises

3.1 basic Predict sizeof for struct { char a; int b; char c; short d; }, then reorder the fields to minimise it.

1 + 3 pad + 4 + 1 + 1 pad + 2 = 12. Reordered as int, short, char, char: 4 + 2 + 1 + 1 = 8.

3.2 think Time summing a 4000×4000 C array row-first vs column-first (gcc -O2, time). Explain the gap.

Column-first is typically 3–10× slower. Each access lands on a different cache line 16 KB away, so every read misses the cache; the row-first loop uses all 16 ints in each 64-byte line it loads.
